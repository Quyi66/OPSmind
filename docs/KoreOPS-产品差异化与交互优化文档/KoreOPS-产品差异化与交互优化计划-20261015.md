## 1. 结论与目标

KoreOPS 已经完成技术框架和部分页面形态的更新，资产清单、自动化工作台、巡检健康度、补丁安装向导都有可继续发展的基础。但业务入口、对象分类、配置表单和部分操作顺序，仍明显延续 Oplus。

建议在现有产品结构内，以“围绕资产发现问题、制定操作计划、追踪执行结果”为业务主线，逐个改进模块内容及页面内部体验。差异化重点落在用户如何理解信息、配置操作和处理结果，不再通过重做整体布局实现。

- **产品识别**：入口结构、核心页面、配置流程和用户可见术语形成统一的 KoreOPS 设计；关键用户路径不再暴露旧平台的品牌与内部模块代号。
- **操作效率**：用户能明确知道当前对象、目标范围、下一步动作、执行进度和失败后的处理方式；减少重新搜索、重复选择和跨模块找记录。

## 4. 修改范围

| 范围 | 执行原则 |

## 5. 页面与模块改造清单

### 5.1 资产模块

- 保留现有清单“在线状态”“连通巡检”的名称、状态判定和展示行为。
- 主机名缺失或为 N/A 时，使用 IP 等有效标识，未知字段保持可辨认。
- 调整清单默认字段、筛选说明和批量操作反馈；保留现有分组/标签侧栏及资产类型标签。
- 在原主机详情容器内整理基本信息、风险、巡检、账户与记录。支持带主机上下文进入相关操作，返回时保留原筛选。

### 5.2 自动化模块

- 在现有工具列表中补充用途、适用范围及参数说明，优化排序和搜索；脚本、命令、REST 等技术类型作为有效筛选保留。
- 工具配置按基础信息、执行内容、运行参数、控制策略和验证分区；低频高级参数按需展开。
- 命令执行页明确目标主机、命令内容与执行范围，区分历史配置和实际运行结果。
- 脚本列表优化新建、上传、版本、审核、同步等按钮优先级，保留现有脚本库/文件库结构。
- 调度页补充可读的时间说明及下次执行时间，具体取决于后台可提供的信息；保留原 Cron 编辑能力。
- 先确认技术任务编排和业务流程的边界，再在模块内部调整名称、顺序和说明。

### 5.3 补丁与漏洞模块

- 沿用现有 Linux/Windows 和功能页面结构，逐项优化模块内部排序、名称与说明。
- 统一页面对 CVE、补丁、软件包和受影响主机的统计说明，保留各自数据口径。
- 包集安装保留现有配置区及目标选择区，增加已选包、目标范围、计划时间、批次、默认不重启和审批要求的摘要。
- 提交后在原页面明确任务 ID、计划时间、审批状态及详情入口，避免只弹出成功消息后丢失追踪上下文。
- 结果页突出失败对象、未执行对象和原因；重试、暂停、恢复及回滚严格依据后台能力。
- 普通补丁、包集、指定软件包可复用选择及反馈逻辑，但不强行合并不同业务接口。

### 5.4 巡检模块

- 保留现有总览、模板、执行记录、结果详情页面结构。
- 优先呈现失败检查项、受影响主机、检查证据和可执行的下一步，再提供脚本路径及详细日志。
- 区分执行失败、检查不通过、人工检查及数据缺失。
- 核对黑名单/白名单的业务含义后优化名称，不能只改文案却改变用户对实际效果的理解。

### 5.5 现有首页面板

- 保留助手、主机、漏洞、资产和巡检区域的位置与整体排布。
- 仅优化面板内部标题、数据口径、排序、加载失败、空值和重试反馈。
- 漏洞缺失评分显示“未评分”，真实 0 分保留；未知数量不回退为 0。
- 近期情报样本明确范围，不以局部查询结果代表全量环境风险。

## 6. 局部交互规则

| 场景 | 页面内优化 |
| --- | --- |
| 筛选 | 明确何时生效，支持回车，保留已选条件，返回恢复筛选及分页 |
| 批量选择 | 区分本页、全部筛选结果和已选项，显示实际范围及数量 |
| 主机选择 | 沿用所在页面现有入口，统一选择反馈；说明分组/标签条目和实际主机数的区别 |
| 表单 | 按任务步骤分区，高级项按需展开，必填项和错误定位清楚 |
| 提交 | 提交前汇总范围、时间、批次、重启和审批要求，防止重复请求 |
| 进度 | 展示真实阶段、更新时间、成功/失败/跳过数量和任务 ID |
| 结果 | 先看结论和失败对象，再展开日志；状态未知不能提示成功 |
| 空与错 | 无匹配、无权限、未采集和请求失败分别表达 |
| 危险操作 | 明确对象及影响范围，保留现有后端权限、审批和确认约束 |

## 8. 接口边界

- 现有前端可先完成：模块内名称和顺序、表格/筛选/表单内容、空值与错误状态、提交摘要、利用已有任务 ID 跳转。
- 需要确认后端：动态主机集合解析及快照、权限过滤、任务 ID 返回结构、任务恢复、失败重试范围、巡检处置记录。
- 包集实际契约结合 [包集接口说明](./patch-package-set-oneclick-api.md)、[定时安装审批接口变更](./本次更新-前端接口-定时安装审批-20260916.md)及现有 API 核对。提交链路按定时审批约束验收，不以早期“立即执行”示例覆盖现行行为；保留管理员/普通用户的审批差异及默认不重启。
- 原始对象 ID、权限 token、用户自定义名称、脚本路径和审计值不盲目替换。内置资源的可读名称与技术详情分开表达。

## 9. 验收与验证

1. 检查全局结构及原有模块入口保持原样，变更集中在目标页面/模块。
2. 验证筛选、分页、选中目标及返回来源的上下文一致。
3. 验证提交前摘要与实际请求一致，提交后有明确追踪入口。
4. 验证评分缺失、真实 0、未知数量、请求失败、未采集等状态。
5. 保留后端权限、审批、租户过滤、时间和重启约束。
6. 优先采用 diff 审查、定向静态检查和必要的业务逻辑测试。按用户要求，不主动运行生产构建或截图级验证。
