#### 专项说明：8/8 补丁「重启策略」502 故障（故障本身已闭环；**但它暴露出的下发路由缺陷是新的 P0 B14**）

这次故障在现场印象比较深，前后端同事可能听说过，因此把完整结论写在这里。**读的时候请把两件事分开：故障（已修完）和造成故障的缺陷（还在）。**

> **注意：根因结论前后修正过两次，本节是 8/11 下午系统侧在 219 上完成实操排查后的最终版本。** 之前流传过两个说法，都不准确：
>
> - **说法一（错）**：「Docker 守护进程重启，宿主机 mariadb 抢占 3306」。已被推翻——219 的 dockerd `NRestarts=0`，**守护进程从未重启过**，当前实例是随最近一次 boot 一起起来的。
> - **说法二（对了一半）**：「219 被放进了常规补丁批次，给自己打了补丁」。219 确实被打了补丁，但**不是因为它在目标清单里**。真正的原因见下，比这严重得多。

**现象**：8/8 在**目标机 94** 上执行补丁安装，四个步骤中 ①预检查成功、②补丁安装成功、③**重启策略失败，前端报 `Request failed with status code 502`**、④脚本校验被第 3 步卡住一直等待。用户后台登录 94 确认**94 并没有重启**，Agent 也没有收到 reboot 命令。

**根因：任务下发打到了错误的主机上——勾选的是 94，实际执行在 219（平台自己）身上。**

系统侧在 219 上取到的证据：

- 平台里**根本没有「批次」这个对象**，每条补丁任务自带一个**显式的 CI id 列表**；8/8 那条任务的列表里**只有 94，没有 219**；
- **94 当天完全没有 dnf 记录**——那 43 个包不是装在 94 上的；
- 43 个包的升级记录出现在 **219** 上，且 219 上存在对应时刻的 **ansible 被控端临时目录**，当时 219 上**装着 agent**，机器上**没有任何自动更新器**（排除了「它自己升的」这种可能）。

也就是说：**平台把一条本该发往 94 的命令，发到了自己身上。**219 升完包后按 `needs-restarting -r` 的判定重启了整机，**正在下发任务的那台机器自己没了**，任务自然断在「重启策略」这一步。

系统侧从 rsyslog 还原出的时间线（全部发生在 **219** 上）：

| 时间（8/8） | 事件 |
|-------------|------|
| 10:04 | 219 上完成一次 dnf 升级，共 **43 个包**。该事务的 `Command Line` 字段为空，说明**不是命令行手工执行**，而是走 DNF API——符合 Ansible `dnf` 模块的特征 |
| 10:05:55 | 执行 `needs-restarting -r`，判定**需要重启** |
| 10:05:56 | 系统开始关机 |
| 10:06:22 | 重启完成 |
| 10:06:28 | 容器内 mariadb 报 `address already in use`，数据库起不来 |

**宿主机 mariadb 抢占 3306 是重启之后的连带现象，不是起因。** 219 上确实存在两套 MariaDB：宿主机那套是手写的 systemd 单元，datadir 在 `/data`，`my.cnf` 里写死 3306，**依赖链比 docker 短，开机时必然抢先拿到端口**。所以整机重启后容器数据库起不来，把一次「重启期间的短暂不可用」拖长成了「重启后持续 502」。

**已排除的可能**：OOM（内核日志无记录）、人为操作（无对应登录与命令记录）、自动更新器（219 上没装）。

**处置（均已完成）**：宿主机那套 MariaDB 已 `systemctl mask`（比 `disable` 更彻底，防止被依赖关系拉起），容器数据库独占 3306；219 上的 agent 也已 `mask`，**平台机器上不再有活着的 agent**，这是比「下发时人工不勾选 219」更硬的边界——后者其实**根本无效，因为 8/8 那次操作者本来就没勾 219**。

**这次 502 故障本身已经闭环，后端不需要做长任务容错。** 早前由这次故障衍生出的「平台不可用时任务状态不丢失 / Agent 重连后续报」这类诉求**已经撤销，本轮不恢复**。本版 B5 保留的是另一件独立的事——指令幂等契约的三项端到端验证，它来自 8/3 报告 §4.1，与本次 502 无关。

> **但是：故障闭环了，导致它的缺陷没有。** 让命令跑错机器的那个下发路由问题**仍然存在于当前平台上，而且不是只影响 219**——8/11 又发现一个 CI 的 CMDB IP 写着 220、实际打在了 101 上。这已立为本清单风险最高的后端条目 **B14**，请务必看。把这次 502 理解成「一次已修好的平台事故」是不够的，它是路由缺陷第一次**恰好打到了平台自己身上**，所以才被发现。

### 0.3 本次新增 / 变更的条目

> ## ⚠ 请先看 B14：任务下发会打到错误的主机上

> **这是本清单里风险最高的一条，高于其它所有条目，包括所有 P0。** 8/11 系统侧在 219 上实操排查后确认：**决定命令落到哪台机器的是 `cmdb_ansible_config` 表里的 agent `client_id`，CMDB 里的 IP 只是展示属性、不参与路由**。两者一旦错位，命令就会在**界面显示正常**的情况下打到另一台机器上。

> 这不是理论风险，已经发生了两次：8/8 那条勾选 94 的补丁任务实际打在了 **219（平台自己）** 上，把平台自己打重启了；8/11 又发现一个 CI 的 CMDB IP 写着 **220**、实际打在 **101** 上。

### 0.5 需运维 / 系统侧决策的遗留风险（**不属于前后端开发任务，不进 F/B 编号**）

这一节记录两件由 8/8 故障复盘带出来的事。它们都**不是**前端或后端的开发工作，不要认领、也不要据此给后端加需求；写在这里是为了让所有人知道风险还在，以及该找谁拍板。

**R1 —— 平台自身被打到的风险：已用「219 上不留活着的 agent」硬隔离，但边界要写进基线【中，已缓解】**

8/8 那次中断的表现是「平台自己被打了补丁并重启」。**注意它的成因已经查清，是下发路由错机（见 B14），不是「219 被放进了补丁批次」**——当时的目标清单里只有 94。因此这里要特别提醒一句：

> **「下发时人工不勾选 219」这类约定是无效的防线。** 8/8 那次操作者本来就没勾 219，命令照样打了过去。任何依赖「操作时注意不要选中平台」的流程约定都挡不住这类问题。

系统侧已经做了比约定更硬的处置：**219 上的 agent 已 `systemctl mask`**，平台机器上没有活着的 agent，路由再错也落不到 219 上。这条边界建议写进部署基线：**平台节点不部署 agent、不作为被纳管对象**，新环境同样执行。

仍需运维侧确认的是：其它承载平台角色的节点（217 执行机、将来可能的备机）是否也适用同一条规则，以及如果确有「平台自身也要打补丁」的需求，走什么独立窗口。

**注意：R1 已缓解，不代表 B14 可以降级。** mask agent 只挡住了「打到 219」这一种情形，**打到其它错误主机（如 8/11 发现的 220 → 101）的路径完全没有被挡住**。

**R2 —— 219 的 systemd journal 是 volatile 的，跨重启查不到历史日志【中】**

这次能还原出 10:04 → 10:06 的完整时间线，**完全是靠 rsyslog 落盘的 `/var/log/messages-*`**；`journalctl` 因为 journal 存在 `/run` 里（tmpfs），重启后前一次 boot 的日志已全部丢失，`journalctl --list-boots` 只看得到当前 boot。

这一条对后端有实际意义：**今后凡是涉及「平台重启 / 容器重建前后」的故障，后端排查时拿不到跨重启的服务日志**，只能依赖 rsyslog 里粒度更粗的部分，可诊断性很差。上一次是运气好——rsyslog 恰好开着且保留了归档。

建议系统侧开启持久 journal（`mkdir -p /var/log/journal` + `journald.conf` 中 `Storage=persistent`，并设置合理的 `SystemMaxUse` 上限），217 与后续纳管的平台类节点同样处理。**这属于运维配置，不需要后端改代码**，因此不编 B 号。

## F1 —— 一键安装命令模板在自签证书环境下不可用【P0，现场最高优先】

**现象 / 背景**

控制台「新增 Agent 主机」向导第 1 步生成的安装命令目前是这种形态：

```bash
curl -fsSL https://192.168.1.219/sjxy-console/agent/install.sh | sudo sh -s -- \
  --token <TOKEN> --server https://192.168.1.219/sjxy-console
```

219 用的是**自签证书**，受管机的系统信任库里没有这张证书。用户把命令复制到目标机执行，第一步就报：

```
curl: (60) SSL certificate problem: self-signed certificate
```

脚本根本没下载下来，安装没有发生。平台侧 `install.sh` 与 `ca-bundle.crt` 本身都是 200，**问题完全在命令模板**，不在 token、不在后端。

除了证书，管道写法 `curl ... | sudo sh` 还有第二个坑：管道下 `install.sh` 内部的交互与错误处理不可靠，**curl 失败时 `sh` 读到空输入并正常退出，整条命令的退出码是 0**——自动化脚本会把失败误判成「安装成功」。现场已经因为这两点反复卡住多次。

**这不是新问题。** 8/3 的《平台阻塞与文档勘误》报告就以勘误项 E1 报过一次：当时在麒麟 V10 端点 94 上执行同样的命令，`curl` 返回 rc=60，原因是该机系统信任库 `/etc/pki/tls/certs/ca-bundle.crt` 只有 **49 字节**（等于空）。这构成一个先有鸡还是先有蛋的死结——**平台的 CA 要靠 `install.sh` 下发，但没有 CA 就拉不到 `install.sh`**。当时给出的建议（先落盘再执行、用 `--ca-cert` 把 CA 一并装给 Agent）至今未落到 UI 的命令模板里，所以同一个问题在 219 上又完整复现了一遍。

> **CA 分发这一半已经修好了（8/11）。** 219 上现在发布的 `ca-bundle.crt` 是 **1354 字节的真实 CA**，指纹与 `:443` 上的实时证书一致，容器重建后仍返回 200；系统侧还加了带校验的发布脚本 `publish-agent-ca.sh`（校验 openssl 能解析、字节数不低于下限、指纹与实时证书一致，任一不满足就拒绝发布）。**所以 8/3 那个「49 字节错误页」的坑在当前配置下不复现，下面第 2 点的 `--ca-cert` 变体现在是真的能用了。**但 E1 的另一半——**命令模板本身**——仍然没改，本条依旧是 P0。

#### 追加约束（8/11 实测）：**Ubuntu / Debian 端点目前只能用 http，不能用 https**

系统侧在 219 上确认，那张自签证书是一张**叶子证书**（`CA:FALSE`，KeyUsage 里没有 `keyCertSign`）。不同发行版的 OpenSSL 对「把一张叶子证书当作信任锚」这件事处理不一致：

| 发行版 | 行为 | 结论 |
|--------|------|------|
| 麒麟（94） | OpenSSL **接受**它作为信任锚 | 94 已成功切到 HTTPS 并稳定在线 |
| Ubuntu | OpenSSL **拒绝**：`openssl s_client` 报 **verify error 21**，Python 报 `CERTIFICATE_VERIFY_FAILED` | **只能走 http** |

Ubuntu 上已逐一试过并全部失败的办法：`pip --cert`、环境变量 `PIP_CERT`、`REQUESTS_CA_BUNDLE`、`update-ca-certificates`——**四种全部无效，唯一能用的只有 curl**（curl 走的是另一套校验路径）。

**这里有一个必须写在 UI 上的陷阱：`curl` 成功不等于 Agent 能连上。** 在 Ubuntu 上用 `curl -k` 甚至 `curl --cacert` 把 `install.sh` 拉下来是能成功的，于是很容易得出「HTTPS 通了」的结论；但 Agent 本体是 Python + `requests`，它走 OpenSSL，**装完之后 `register` 会一路 `CERTIFICATE_VERIFY_FAILED`，表现为「装是装上了，就是永远不报到」**。**请不要只用 curl 验证连通性。**

**影响**

「复制粘贴即可安装」这个核心卖点在当前环境下 100% 失败。每台新机器都需要人工改命令，纳管无法交给一线运维自助完成。

**期望行为**

1. Linux 模板改为 **`-k` + 先落盘再执行**（不要用管道）：

```bash
curl -fsSLk -o /tmp/koreops-install.sh https://192.168.1.219/sjxy-console/agent/install.sh && \
sudo bash /tmp/koreops-install.sh --token '<TOKEN>' --server https://192.168.1.219/sjxy-console
```

2. 同时在 UI 上提供**更稳妥的 CA 变体**（推荐给正式环境，等平台换成受信任证书后可作为默认）：

```bash
curl -fsSLk -o /tmp/koreops-ca.crt https://192.168.1.219/sjxy-console/agent/ca-bundle.crt && \
curl -fsSL --cacert /tmp/koreops-ca.crt -o /tmp/koreops-install.sh https://192.168.1.219/sjxy-console/agent/install.sh && \
sudo bash /tmp/koreops-install.sh --token '<TOKEN>' \
  --server https://192.168.1.219/sjxy-console \
  --ca-cert /tmp/koreops-ca.crt
```

3. 新增 **Windows（PowerShell）模板**（配合 F8）：

```powershell
$ErrorActionPreference = 'Stop'
# PowerShell 5.1 下临时接受自签证书；PowerShell 7 请改用 Invoke-WebRequest -SkipCertificateCheck
[System.Net.ServicePointManager]::ServerCertificateValidationCallback = { $true }
$dst = "$env:TEMP\koreops-install.ps1"
Invoke-WebRequest -Uri 'https://192.168.1.219/sjxy-console/agent/install.ps1' -OutFile $dst
& $dst -Token '<TOKEN>' -Server 'https://192.168.1.219/sjxy-console'
```

4. 命令块下方补一行常见故障提示：**「装完后若手工运行 Agent 报 `requests is required`，说明依赖没装全，执行 `/opt/koreops-agent/venv/bin/pip install requests paramiko` 后 `systemctl restart koreops-agent`」**（Ubuntu 上已实际遇到）。

5. **按目标 OS 渲染协议（本轮新增，与上面几点同等重要）**：向导第 1 步已经要选目标操作系统（见 F8），请用这个选择决定命令里的协议，**不要固定写 https**：

   | 目标 OS | 下载地址 | `--server` 参数 |
   |---------|----------|-----------------|
   | 麒麟 / RHEL 系 | `https://192.168.1.219/...` | `https://192.168.1.219/sjxy-console` |
   | **Ubuntu / Debian** | **`http://192.168.1.219/...`** | **`http://192.168.1.219/sjxy-console`** |
   | Windows | 见上面第 3 点 | 同麒麟 |

   Ubuntu/Debian 那一行旁边要有一句可见的说明，例如：**「当前平台证书为自签叶子证书，Ubuntu/Debian 的 OpenSSL 不接受，只能走 http；待平台换发内网 CA 证书后（见 D4）恢复 https。」** 这个 http 例外**必须是临时的、可一键切回的**——建议把协议做成按环境/按 OS 的渲染规则而非写死，等 D4 决策落地后改一处即可。

**验收方式**

- 在一台**干净的**、未导入 219 证书的**麒麟**机器上复制 UI 命令执行，能装完并在「等待报到」里看到该 Agent；
- 在一台**干净的 Ubuntu** 机器上复制 UI 命令（应为 http 版本）执行，同样能装完并**成功报到**——注意这一步的判据是「Agent 在平台上出现并保持在线」，**不是「curl 下载成功」**；
- 反向验证陷阱：在 Ubuntu 上手工用 https 版命令装一遍，应能观察到「安装成功但 Agent 一直不报到、日志里是 `CERTIFICATE_VERIFY_FAILED`」，确认 UI 没有给 Ubuntu 发 https 模板；
- 故意把 token 改错，命令的**退出码非 0**，且屏幕最后一行是可读的失败原因（验证「不再被管道吞掉退出码」）；
- Windows 模板在一台 Win10 / Server 2019 上可复制即装（依赖 F8 与 Agent 端 W3/W7 产物就绪）。

**依赖**

- 依赖我方（Agent 端）A1/A2：`install.sh` 目前存在「pip 失败即中断、但 venv 已建」的半成品路径，前端改完模板后，这类失败会更容易暴露出来，两边最好同期上线。
- Windows 模板依赖我方 W3（`koreops-agent.exe`）与 W7（`install.ps1`）产出，**前端可先按上述形态把模板位占好，不必等**。
- 若后续平台换成内网 CA 签发的受信任证书（见「待决策 D4」），模板可回退到严格校验的 `curl -fsSL`，届时前端需要一个开关或按环境渲染。

## F2 —— 「等待报到」列表为空时没有任何原因说明【P0】

**现象 / 背景**

向导第 2 步「等待报到」是一个空列表 + 「手动刷新」按钮。当目标机因为各种原因没注册成功时，这个页面**永远显示「暂无数据」**，不给任何提示。用户的自然反应是反复点刷新，实际现场卡住过多次。

真实原因通常是下面几种，但界面上完全看不出来：

| 真实原因 | Agent 日志特征 |
|----------|----------------|
| token 已用尽（`maxUses` 一般设为 1，装过一次就消耗掉了） | `401` + `ENROLL_TOKEN_INVALID`，token 状态 `exhausted` |
| token 已过期 | 同上 |
| 用的是上一次向导生成的旧 token | 同上 |
| Agent 服务没起来（依赖没装全） | `requests is required` / 服务 `inactive` |
| 安装根本没发生（F1 那个 `curl: (60)`） | 目标机上没有 `koreops-agent.service` |

**影响**

一线运维无法自助定位，每次都要找我方或后端看日志。

**期望行为**

1. 「等待报到」空列表时展示结构化空态，把上表变成用户能对照的排查清单，并给出目标机上可直接复制的两条命令：
   `systemctl status koreops-agent --no-pager` 与 `journalctl -u koreops-agent -n 40 --no-pager`。
2. 页面上展示**当前这张凭证的实时状态**（数据来自 `GET .../cmdb/api/cmdb/agent/enrollment-token/<tokenId>`）：剩余可用次数、过期时间、是否已被消耗。**只要状态是 `exhausted` 或已过期，就直接提示「这张凭证已不可用，请回上一步重新生成」，不要让用户继续刷新。**
3. 明确文案：「本列表只显示用**当前这张凭证**注册成功的 Agent；换过凭证请回第 1 步重新生成并重装」。
4. 列表出现记录后不会自动勾选，需提示用户「请勾选该行后再进入下一步」（现场也踩过）。

**验收方式**

- 用一张已消耗的 token 走向导，第 2 步能直接看到「凭证已用尽」而不是「暂无数据」；
- 目标机未安装 Agent 时，页面给出的排查清单能让一个没参与过本次排查的运维自行定位。

**依赖**

依赖后端 B3 把凭证状态（剩余次数、过期时间、`exhausted` 标记）通过接口吐出来。若后端暂未就绪，前端可先落地静态排查清单（第 1、3、4 点），不阻塞。

## F3 —— 客户端被踢下线后，重新上线的路径在 UI 上不存在【P1】

**现象 / 背景**

平台侧把某台机器踢下线 / 解绑后，该机的 `clientToken` 立即作废。Agent 进程还活着，它会用本地配置里的**旧 enrollment token** 反复重注册，得到 `401 ENROLL_TOKEN_INVALID`。8/10 在 94 上实测：从 14:05:43 起每 3 秒刷一条错误日志，持续数小时。

用户这时打开控制台，只能看到该主机离线，界面**没有任何入口告诉他"要重新签发凭证并在目标机重装"**，他会去点「等待报到」然后卡在空列表（即 F2）。

**影响**

一次踢下线就等于一次人工返场，且现场无法自助恢复。

**期望行为**

1. 设备详情 / 列表中，对状态为「离线且凭证已失效」的主机，提供明确的 **「重新纳管」** 入口，一键跳到「新增 Agent 主机」向导并预填该主机的 CMDB 资产。
2. 该入口的说明文案要写清目标机上的完整动作，可直接复制：

```bash
systemctl stop koreops-agent
rm -f /etc/koreops-agent/state.json      # 清掉已作废的 clientToken
curl -fsSLk -o /tmp/koreops-install.sh https://192.168.1.219/sjxy-console/agent/install.sh
sudo bash /tmp/koreops-install.sh --token '<新token>' \
  --server https://192.168.1.219/sjxy-console \
  --ca-cert /etc/koreops-agent/ca-bundle.crt
```

3. 若后端按 B3 提供了独立的 re-enroll 通道，这里应改为「下发重新纳管指令」，无需用户去目标机操作——这是更理想的形态，前端预留位置。

**验收方式**

从控制台踢下线 94，随后仅凭界面上的引导（不看任何文档、不问我方）就能把它重新纳管上线。

**依赖**

- 与我方 A6 配套：Agent 端会把这种永久失效的退避从 3 秒升到分钟级，并只提示一次「需重新纳管」，不再刷屏。
- 与后端 B2 配套：后端需要用可区分的错误码（如 `NEED_REENROLL`）告诉 Agent「不要再重试了」。

## F4 —— 「绑定到已有资产档案(Local)」与「跳板代理模式(Gateway)」容易误选，报错文案不解释原因【P1】

**现象 / 背景**

向导第 3 步「确认绑定」有两种纳管模式。现场实际卡点：

- 用户为一台**自己已装 Agent 并报到成功**的机器（94）选了 Gateway，界面弹「跳板代理模式下请输入目标主机 IP」。用户不理解为什么要填另一个 IP，反复试错。
- 选 Local 但没选资产时弹「请选择要关联的目标 CMDB 主机」，提示语没有说明「资产要先在 CMDB 里存在」（接着就撞上 F5）。

两种模式的语义其实很清楚，但界面上没写：**Local = 这台机自己装了 Agent，把它和自己的资产档案绑上；Gateway = 用一台已在线的 Agent 当跳板，去管另一台没装 Agent 的机器。**

**影响**

首次纳管的用户几乎必然误选一次，每次误选都要人工解释。

**期望行为**

1. 默认选中 **Local**；Gateway 需要用户主动切换。
2. 两个选项下各加一句说明（就用上面那两句话），Gateway 再补一句「目标主机 IP = 你要通过跳板去管的那台机器的 IP，不是当前 Agent 所在机器的 IP」。
3. 当候选 Agent 的上报 IP 与「目标主机 IP」填写值相同时，主动提示「这两个 IP 相同，你可能想用的是 Local 模式」。
4. 校验失败的提示语要说明**为什么**需要这个字段，而不是只说字段为空。

**验收方式**

一位没用过该向导的运维，为一台已装 Agent 的机器完成绑定，全程不需要外部说明、不出现模式误选。

## F5 —— 没有任何 CMDB 资产时，绑定这一步是死路【P1】

> 延续 7/29-F2 的后半段。7/29 任务单要求纳管向导支持「**选**或**建**主机 → 签发 → 展示安装命令」，「选」已经做了，「**建**」一直没做，本条把它单列出来。

**现象 / 背景**

Agent 报到**不会自动创建** CMDB 主机档案。全新环境（219 就是这种情况）里，「选择目标资产」下拉框是空的，用户没法完成绑定，界面也没告诉他"要先去别的模块建一条资产"。现场实际发生过：用户反复打开选择器，以为是加载失败。

**影响**

首次纳管必须先跳出向导去 CMDB 建档案，再回来重走一遍，流程割裂；不熟悉平台的用户会直接卡死。

**期望行为**

1. 「选择目标资产」为空时，展示空态文案：「Agent 报到不会自动创建资产档案，请先创建一条对应的 CMDB 主机」，并在空态里直接放「导入新资产」按钮（现在这个按钮存在但不显眼，且空态没有说明）。
2. **更好的做法**：支持用 Agent 已上报的信息**内联创建资产**。Agent 在 `register` 时已经上报了 `hostname`、`ip`、`os`、`agentVersion`、`capabilities`，这些字段足以预填一条主机档案，用户确认即可，不必跳出向导。
3. 创建完成后自动回填到「选择目标资产」并选中。

**验收方式**

在一个 CMDB 里没有任何主机的租户下，从「生成凭证」到「确认绑定」全程在向导内完成，不需要跳到其它模块。

## F6 —— 需要区分展示「Agent 当前 IP」与「CMDB 纳管 IP」【P1】

**现象 / 背景**

Agent 每次 `register` 都会上报它当前的出口 IP（按到平台的路由动态算出来）。而 CMDB 资产档案里的主 IP 是绑定时写死的。DHCP 环境下这两个值会分叉，但界面上现在只有一个「IP」，用户分不清自己看到的是哪一个，也不知道该改哪个。

**影响**

**验收方式**

在 94 上改成另一个 IP 后重启 Agent：列表里「Agent 上报 IP」跟随变化，「CMDB 纳管 IP」保持不变并出现不一致标记；点同步后两者一致，且能在变更记录里查到这次同步。

**依赖**

强依赖后端 B1（字段与同步接口）。B1 属于**待决策**事项，未定之前前端可先做展示分列（第 1 点），同步按钮留位。

**期望行为**

| 场景 / 错误 | 前端提示方向 |

## F8 —— 纳管向导按目标操作系统分流（Windows 支持）【P0】

## F9 —— 设备列表展示 OS 类型与 Agent 平台，按平台与能力启用操作【P1】

> 合并并扩展三条历史条目：8/7-F2、7/29-F3（主机列表增加 Agent 字段）、7/29-F4（补丁按钮按「在线 + capabilities + 后端授权」启用/禁用）。7/29-F3 的字段目前已基本具备（列表已能看到接入通道、Agent 版本、状态、能力、最后在线时间），**本条剩下的增量是 `os` / 平台维度，以及 7/29-F4 那套按钮启用规则**。

**现象 / 背景**

Agent 在 `register` 时上报的 `os` 字段格式是 `"<系统> <版本>"`（由 `platform.system()` + `platform.release()` 拼出），Linux 上例如 `Linux 4.19.90-...`，Windows 上会是 `Windows 10` / `Windows 2019Server` 之类。当前列表没有把它单列出来。

Windows 与 Linux 的能力差异是实打实的：Linux 走 yum/apt，Windows 走 Windows Update（WUA）；Linux 的补丁回滚是 `yum history undo`，Windows 是 `wusa /uninstall /kb:`，且**有相当一部分更新根本不可卸载**。

**影响**

界面上对一台 Windows 主机点出「Linux 补丁安装」这类操作，任务必然失败，且失败原因对用户完全不可理解。

**期望行为**

1. 列表新增列：`os`（操作系统）、Agent 平台（Linux / Windows）；确认 `agentVersion`、`capabilities`、`lastSeenAt`、`connectionType`、`clientId`、`agentStatus` 均已可见并可按 SSH / Agent 筛选。
2. 补丁 / 巡检等操作按钮按 **在线状态 + `capabilities` + 平台 + 后端授权** 四个维度启用或禁用，禁用时 tooltip 说明原因（例如「该主机为 Windows，请使用【补丁漏洞 → Windows】入口」「Agent 当前离线」）。
3. **注意 7/29 就强调过的一个语义**：Agent 声明的 `rollback` capability 只表示「通道能执行回滚指令」，**不等于补丁回滚业务已经开放**。按钮的启用条件里要包含后端的业务授权，不能只看 capability 字符串。
4. 「补丁漏洞 → Linux」与「补丁漏洞 → Windows」两个入口的主机选择器要各自按平台过滤。

**验收方式**

同时纳管一台 Linux 与一台 Windows 主机，两者在列表中平台标识正确，且互相点不出对方专有的操作；把其中一台 Agent 停掉，相关操作按钮在离线后变为禁用并给出原因。

**依赖**

依赖后端 B10（平台按 `os` 字段分流指令）。

## F10 —— Windows 补丁结果展示适配【P1】

**现象 / 背景**

Windows 的补丁数据模型与 Linux 不同：标识是 **KB 号**（如 `KB5034441`）而不是软件包名+版本；安装结果里有 **`rebootRequired`** 标记；卸载时存在「该更新不可卸载」这一合法终态；WUA 的失败会返回 HRESULT 形式的错误码（如 `0x80240034`）。

**影响**

若沿用 Linux 的展示，Windows 补丁任务的结果会显示成空白或「未知失败」，用户无法判断到底成没成。

**期望行为**

1. 「补丁漏洞 → Windows」相关页面（主机概览 / CVE 列表 / 补丁任务中心 / 安装回滚历史）按 KB 号展示，含标题、严重级别、是否需重启。
2. 安装完成后若 `rebootRequired = true`，在任务结果里明确提示「需重启才能生效」，并与「重启策略」步骤联动。
3. 回滚（卸载）时，对不可卸载的更新展示为**明确的「不支持卸载」终态**，不要显示成失败，也不要显示成成功。
4. WUA 错误码展示原始 HRESULT + 可读说明。

**验收方式**

对一台 Windows 主机完成一次「扫描 → 安装 → 回滚」，三个环节的结果在界面上都可读；对一个不可卸载的更新执行回滚，界面明确告知不支持而非报错。

**依赖**

依赖我方 W5（WUA 补丁能力，返回结构会与 Linux 版对齐）与后端 B11（数据模型入库）。

## B1 —— DHCP 环境下客户端 IP 变化的处理策略【P0，待决策】

**现象 / 背景**

Agent 的身份锚点是 `clientId`（由机器指纹生成，Linux 上取自 `/etc/machine-id`）与落盘的 `clientToken`，**不是 IP**。所以 DHCP 换 IP 不会让平台把它当成另一台机器。

但现状有一个明确的缺口：**Agent 只在 `register` 时上报 `ip` 字段，`poll` 请求只带 `clientId`，不带 IP。** 也就是说，一台长期在线、不重启的 Agent 换了 IP 之后，平台在下一次 `register` 发生前不会知道。而 CMDB 资产档案里的主 IP 是绑定时写入的，目前没有任何自动同步逻辑。

用户明确提出了这个场景，需要产品拍板。

**我方建议（详细论证见第三章 D1）**

**分两层处理：运行态 IP 自动更新，配置态（CMDB 主 IP）默认不覆盖。**

| 字段 | 建议 | 理由 |
|------|------|------|
| Agent 运行态 IP / `lastSeenIp` | **自动更新，随时刷新** | 它表达的是「此刻怎么连上这台机」，DHCP 场景下必须跟随 |
| CMDB 资产主 IP / 纳管 IP | **默认不自动覆盖**，改为「检测到变化 → 提示 → 可选同步」 | CMDB 主 IP 常被工单、审计、防火墙策略、SSH 纳管通道引用，静默改写风险大；DHCP 短租约还会让资产库反复抖动 |
| 变更记录 | 自动记录「原 IP → 新 IP → 变更来源（clientId）」 | 便于审计与排障 |

**影响**

不做：DHCP 环境下界面长期显示旧 IP，运维照着它去连机器会连错。
做成「无条件自动覆盖」：CMDB 数据被 DHCP 抖动改乱，且可能覆盖掉人工填写的管理地址 / VIP，牵连 SSH 纳管通道。

**期望行为（后端具体改动）**

1. **新增运行态 IP 字段并保证它会更新。** 建议在 `host_agent_binding`（或等价的 Agent 运行态表）上增加 `last_reported_ip`、`last_reported_at`。
   - 配套：需要一条能周期性携带 IP 的通道。当前 `GET .../agent/api/agent/poll?clientId=` 不带 IP，两种改法二选一：
     - **（推荐）** `poll` 增加可选查询参数或请求体，允许 Agent 附带当前 `ip`/`hostname`；
     - 或由 Agent 侧在检测到本机 IP 变化时主动重新调用 `register`（这属于我方改动，见「依赖」）。
2. **CMDB 主 IP 默认不覆盖**，但要能查出不一致：`GET .../cmdb/api/cmdb/agent/host-info` 的返回体中同时给出 CMDB 主 IP 与 `last_reported_ip`，并给一个 `ipMismatch` 布尔字段，供前端 F6 展示。
3. **新增显式同步接口**，例如 `POST .../cmdb/api/cmdb/agent/sync-ip`，体 `{"clientId":"...","hostId":"...","confirm":true}`，语义为「把 CMDB 主 IP 更新为该 Agent 当前上报 IP」。要求幂等，并写审计。
4. **提供租户级开关**「DHCP 环境：允许自动同步资产主 IP」，默认关闭。开启后可自动同步，但仍需写审计。
5. **自动同步的收敛条件**（即使开关打开也建议限制）：仅在「CMDB 主 IP 为空」或「新 IP 与上一次上报 IP 一致（说明已稳定，不是抖动中）」时执行。
6. **所有 IP 变更写审计日志**，字段至少含：hostId、clientId、原 IP、新 IP、触发方式（自动 / 人工确认）、操作人、时间。
7. **顺带把在线状态同步的时延确定下来**（7/29-B9 提过但从未验收）：`register` / 心跳 / 掉线三个事件驱动主机的 `agentStatus`，**约定的指标是 90 秒内上下线状态正确**。这一条和上面的 IP 上报共用同一条通道，建议一起设计——**如果最终选择"`poll` 携带 IP"的方案，`poll` 本身就是天然的心跳，两个需求一次解决。**

**验收方式**

- 把 94 换到另一个 IP 并重启 Agent：设备列表的「Agent 上报 IP」在一个心跳周期内变为新值，CMDB 主 IP 保持旧值且被标记为不一致；
- 停掉 94 的 Agent 服务，90 秒内列表状态变为离线；重新启动后 90 秒内恢复在线；
- 调用同步接口后 CMDB 主 IP 变为新值，且审计里能查到这条变更；
- 打开租户开关后重复上述过程，主 IP 自动跟随，审计同样有记录。

**依赖**

若采用「Agent 主动 re-register」的方案，需要我方在 Agent 端增加 IP 变化检测并触发重注册——**这是小改动，后端定了方案我方即可跟进**。请后端先明确走 `poll` 带 IP 还是走重注册，避免两边互等。

## B2 —— 踢下线 / 凭证失效需要可区分的错误码【P0】

**现象 / 背景**

平台把主机踢下线后，`clientToken` 作废，Agent 的 `poll` 开始返回 401。Agent 会拿本地的旧 enrollment token 去重注册，后端返回：

```json
{"ok":false,"errorCode":"ENROLL_TOKEN_INVALID","message":"enrollment token 无效"}
```

问题在于：从 Agent 的角度看，**「网络抖动导致的临时 401」和「凭证已被永久作废」返回的是同一类错误**，Agent 无法判断该不该继续重试。8/10 在 94 上的实测结果是每 3 秒重试一次、持续数小时（我方 Agent 侧的退避上限被写死在 3 秒，这一半是我方的 bug，见「依赖」），日志刷屏，同时对平台产生无谓压力。

**影响**

受管机日志被污染；平台侧承受无意义的高频请求；运维从日志里也看不出「到底是网络问题还是要重新纳管」。

**期望行为**

1. 区分并明确以下几种失效，各自使用不同的 `errorCode`，并在响应中给出 `retryable: true/false`：

| 场景 | 建议错误码 | retryable |
|------|-----------|-----------|
| clientToken 被平台作废（踢下线 / 解绑） | `NEED_REENROLL` | false |
| enrollment token 已用尽 | `ENROLL_TOKEN_EXHAUSTED` | false |
| enrollment token 已过期 | `ENROLL_TOKEN_EXPIRED` | false |
| enrollment token 不存在 / 格式错 | `ENROLL_TOKEN_INVALID` | false |
| 后端临时故障（DB 不可用等） | 现有 5xx | true |

2. 对 `retryable: false` 的情况，响应里给一句面向人的 `message`，例如「该主机已被解除纳管，请在控制台重新签发凭证后重装 Agent」——这句话会直接出现在受管机日志里，是现场唯一能看到的提示。
3. **顺带确认解绑留痕**（7/29-B3 要求过，未验收）：基于 `host_agent_binding` 的绑定 / 解绑操作要写审计，`host_id ↔ client_id` 的历史关系可查。踢下线属于解绑的一种，出问题时需要能回答「这台机是谁在什么时候解绑的」。

**验收方式**

- 从控制台踢下线 94，观察 `journalctl -u koreops-agent`：应看到一条明确的 `NEED_REENROLL` 及可读提示，而不是每 3 秒一条 `ENROLL_TOKEN_INVALID`；
- 该次解绑能在审计记录里查到操作人与时间。

**依赖**

与我方 A6 成对：Agent 侧会依据 `retryable=false` 把退避升到分钟级并只提示一次。**后端出错误码、我方改退避，两边都要做，缺一条效果减半。** 在后端就绪前，我方会先按「连续 N 次 `ENROLL_TOKEN_INVALID` 视为永久失效」兜底，但这不如显式错误码可靠。

## B3 —— enrollment token 的生命周期与「重新上线」通道【P0，部分待决策】

**现象 / 背景**

目前的 enrollment token 是一次性凭证：签发时指定 `ttlMinutes` 与 `maxUses`（UI 上单机默认 1 次），装过一次就变成 `exhausted`。这套设计对**首次纳管**是合理的，但对**已注册主机的重新上线**很别扭——现在只能让用户回到向导重新签发一张一次性 token、去目标机清 `state.json` 再重装一遍。

同时，token 的规则从未被文档化，现场反复踩：用户不知道 token 是一次性的，也不知道装失败也算消耗（哪怕安装到一半失败，这张 token 也废了）。

**影响**

每次踢下线 / 主机重装 / 状态文件丢失都要走一遍完整重装流程；用户对「为什么刚生成的 token 又不能用了」长期困惑。

**期望行为**

1. **明确并文档化 token 规则**，并通过接口暴露给前端（供 F2 展示）：
   - 默认 `ttlMinutes` 与 `maxUses` 是多少、UI 上限是多少；
   - 「消耗」的判定时点是什么（`register` 成功时消耗？还是请求到达即消耗？——**现场按「装失败也算消耗」的行为在走，请确认这是不是预期**）；
   - 是否支持一张 token 批量装多台（`maxUses > 1` 的语义）；
   - `GET .../cmdb/api/cmdb/agent/enrollment-token/<tokenId>` 返回体中包含 `status`（`active` / `exhausted` / `expired`）、`remainingUses`、`expiresAt`。
2. **【待决策】为「已注册主机重新上线」提供独立通道**，不要复用一次性 enrollment token。我方建议见第三章 D2，核心是：已经绑定过的主机应该能凭 `clientId` + 机器指纹申请一张新的 `clientToken`，由管理员在控制台「批准重新上线」，而不是让用户去目标机上重装。
3. 无论是否做第 2 点，**至少要让重新签发的 token 能被 Agent 就地更新**，即支持只更新凭证而不重装整个 Agent。

**验收方式**

- 前端能在向导第 2 步实时显示凭证状态（配合 F2）；
- 踢下线后的主机，按最终选定的方案能在 5 分钟内恢复在线，且过程不需要 SSH 登录目标机（若采纳第 2 点方案）。

**依赖**

第 3 点需要我方在 Agent 端支持「凭证热更新」（读到新 token 后不重启服务即生效），后端确定接口后我方跟进。

## B4 —— 后端返回的 `installCommand` 要与前端 F1 模板口径一致【P1】

**现象 / 背景**

`POST .../cmdb/api/cmdb/agent/enrollment-token` 的响应里带一个 `installCommand` 字段。如果前端按 F1 改了模板，而后端这个字段还是老的 `curl -fsSL ... | sudo sh`，就会出现「界面上是新命令、接口里是旧命令」的分裂——文档、邮件通知、API 调用方拿到的都是会失败的那条。

**影响**

前端修好了，从其它路径（API、通知、导出）拿到命令的用户仍然踩同一个坑。

**期望行为**

1. `installCommand` 与 F1 的模板保持字面一致（含 `-k`、先落盘、`--ca-cert` 变体）。
2. 增加 `installCommandWindows` 字段，返回 PowerShell 版本。
3. 建议把命令模板做成**服务端配置项**而非硬编码，这样将来平台换成受信任证书（见 D4）时改一处即可。
4. **协议必须按目标 OS 区分（本轮新增）**：接口要能按目标操作系统返回不同协议的命令——**Ubuntu / Debian 返回 `http://...`，麒麟等返回 `https://...`**，理由与实测证据见 F1 的「追加约束」一节。具体做法建议给签发接口加一个可选入参（如 `targetOs`），或在响应里同时给出 `installCommandLinuxHttps` 与 `installCommandLinuxHttp` 并标注适用范围。**这一条同样适用于后端产出的所有文档、邮件通知与导出内容**，口径要统一，不要出现「界面是 http、手册是 https」。

**验收方式**

- 调接口拿到的 `installCommand` 直接粘到干净的受管机上可执行成功，与 UI 上复制的命令字面一致；
- 指定目标 OS 为 Ubuntu 时返回的是 http 版本，指定麒麟时返回 https 版本；
- 用返回的 Ubuntu 版命令在干净 Ubuntu 上装完后，**Agent 能真正报到并保持在线**（不是只验证下载成功，原因见 F1）。

## B5 —— 指令幂等契约：补做三项真实平台环境下的端到端验证【P1】

> **本条与 8/8 那次补丁「重启策略」502 无关，别把两件事合起来做。** 那次故障的真实根因是**下发路由错机**——勾的是 94，命令实际打在了 219（平台自己）上，219 升完包后自行重启，下发指令的机器自己没了；宿主机 mariadb 抢 3306 只是重启后的连带现象。**故障本身已闭环，后端不需要做任何长任务容错改造**（该诉求已撤销且不恢复）；**产生它的路由缺陷另立为 B14**，那才是 8/8 那件事的整改项。本条留下的是第三件事：Agent 与平台之间的**指令幂等契约从未在真实平台上验证过**。

**现象 / 背景**

我方 Agent 端很早就实现了指令幂等：用落盘的命令历史状态机（`executing` / `done` / `reported`）替代进程内存里的已上报集合，进程重启后不会重复执行同一个 `cmdId`；结果上报失败会先 spool 到本地，重连后按 `cmdId` 幂等补报。

**但 8/3 报告 §4.1 已经写明：这套演练当时是用我方自建的 stub relay 做的，不是真实平台。** 以下三点在真实平台上从未验证过，从 8/3 挂到现在：

1. 真实平台 Relay 在 Agent 重启后，**是否会重投同一个 `cmdId`**；
2. `DISPATCH_TIMEOUT` 与 Agent 上报的 `rc=124`（执行超时）之间**如何交互**，两者冲突时平台按哪个为准；
3. 平台**是否接受** Agent 在断连恢复后的补报结果（同一 `cmdId` 的重复 `POST /result`）。

「重启不重复执行」是联调手册 §7 点名的头号风险。**在这三点验证完成之前，它只能算在 Agent 单侧关闭，不能算端到端关闭**——8/7 版清单 B8「业务闭环从未在一个功能齐全的 war 上跑通过」剩下没关的就是这一块。

**影响**

如果平台在 Agent 重启后确实会重投 `cmdId`，而幂等链路某一环没对上，后果是**同一条指令被执行两次**。对补丁安装、重启这类操作，重复执行的代价很高。这个风险目前是「大概率没问题，但没人验证过」的状态。

**期望行为**

1. 后端明确并文档化 `cmdId` 的重投策略：什么条件下会重投、重投几次、间隔多久。
2. 后端明确 `DISPATCH_TIMEOUT` 与 `rc=124` 的优先级：平台侧判超时后，若随后又收到 Agent 上报的 `rc=124`，以哪个为准，任务终态如何记录。
3. 后端确认对同一 `cmdId` 的重复 `POST /result` 稳定返回 200 或 409，**不当成异常、不产生重复记录**。这一条我方 Agent 侧已经实现，只需要后端确认现有实现已满足即可，**成本很低，建议先做这条**。
4. 三点确认完成后，与我方一起做一次联合演练（见验收方式）。

**验收方式**

在 219 / 217 / 94 这条真实链路上做一次演练：下发一条耗时较长的指令，执行中途 `SIGKILL` 掉 Agent 进程，然后重启 Agent。期望结果是——该指令**不被重新执行**，结果以 `rc=124` 上报**一次**，平台接受该补报并把任务置为确定的终态，任务详情里不出现重复记录。

**优先级说明**

原先这条是 P0，驱动因素是 8/8 那次 502 暴露的「长任务卡死」。**该驱动因素已消失（那次故障的根因是下发错机，整改项是 B14，不需要后端做容错改造），因此下调为 P1。** 保留 P1 而不是 P2，是因为它关系到「指令会不会被执行两次」这个正确性问题，且在 Windows 端点铺开、纳管规模上去之前应该关掉。

**依赖**

Agent 侧的幂等状态机与 spool 能力**已经实现**，后端不需要等我方；第 4 点的联合演练需要我方配合，随时可约。

## B9 —— Windows 专用 playbook（Windows 支持的最大依赖）【P0】

**现象 / 背景**

这一条是 Windows 支持能否达成「含补丁能力」目标的**关键前置**，请优先评估。

我方的 `koreops_agent.py` 是一个标准 Ansible 连接插件（实现 `exec_command` / `put_file` / `fetch_file`）。Ansible 执行任务时的固有行为是：**先把 Python 模块代码推送到目标机，再用 POSIX shell 调用目标机上的 Python 解释器执行**。8/8 那次 `Gathering Facts` 失败就是这个链路。

Windows Agent 按既定方案打包成 PyInstaller 单 exe，**目标机上没有独立的 Python 解释器**，也没有 POSIX shell。因此现有的 Linux playbook 在 Windows 主机上**必然失败**，这不是配置问题，是机制问题。

**影响**

不做这条，Windows 侧只能退回到「基础通道 + 我方自研补丁指令」，无法复用平台现有的补丁流程与数据模型，与「Windows 端点含补丁能力」的目标不符。

**期望行为**

1. 为 Windows 主机**单独提供 playbook**（补丁扫描 / 安装 / 回滚 / 巡检），使用 `win_*` 系列模块或直接下发 PowerShell 指令。
2. inventory 中对 Windows 主机设置 `ansible_shell_type: powershell`（我方插件 W6 会支持这个 shell 类型与 Windows 路径语义）。
3. 平台在组装任务时按主机的 `os` 字段选择对应的 playbook。

**验收方式**

对一台已纳管的 Windows 主机执行补丁扫描，任务能正常完成并返回结构化结果（不再出现 `Gathering Facts` 失败）。

**依赖**

我方 W6 负责插件侧的 shell 类型与路径语义。**这一条我方无法替代后端完成**——插件能把 shell 切成 PowerShell，但无法让 Linux 的 Python 模块在一台没有 Python 的 Windows 上跑起来。建议尽早评估，这条不定，W5（Windows 补丁能力）无法端到端验收。

## B10 —— 平台按 `os` 字段分流指令，不要把 Linux shell 指令下发给 Windows Agent【P0】

**现象 / 背景**

Agent 在 `register` 时上报 `os` 字段（格式 `"<系统> <版本>"`，由 `platform.system()` + `platform.release()` 生成）。平台目前下发的执行指令默认是 POSIX shell 语法，Windows Agent 收到后会用 PowerShell 执行，语法不兼容。

**影响**

Windows 主机上的所有指令类操作（exec、脚本下发、巡检）都会失败或产生非预期结果。

**期望行为**

1. 平台在下发任何 `exec` 类指令前，按绑定记录里的 `os` 字段判断目标平台。
2. 建议在 Agent 面的指令协议里增加 `shell` 字段（`sh` / `powershell` / `cmd`），由平台显式指定，Agent 按字段选择解释器——这比让 Agent 猜更可靠。
3. 需要跨平台的通用操作（如「获取磁盘使用率」）应在平台侧维护两套指令模板。

**验收方式**

## B14 —— 任务下发按 `client_id` 路由、CMDB IP 不参与校验，命令会打到错误的主机上【P0，本清单风险最高】

> **这条的风险等级高于本清单里其它所有条目（包括其它 P0）。** 其它条目最坏的后果是「装不上、看不懂、体验差」；**这一条的后果是在生产环境把补丁、重启、任意命令打到非预期的主机上，而且界面上看不出任何异常**。请优先排期。

**现象 / 背景**

8/11 系统侧在 219 上做实操排查，查明了一条一直没人注意到的路由规则：

- 平台里**没有「批次」这个对象**。每条补丁任务自带一个**显式的 CI id 列表**，用户在界面上勾哪几台就是哪几台，不存在「批次里混进了别的机器」这种可能。
- 但**真正决定命令落到哪台机器上的，是 `cmdb_ansible_config` 表里的 agent `client_id`**。
- **CMDB 里的 IP 只是一个展示属性，完全不参与路由，也不参与任何校验。**

也就是说，界面上的「这台机器」和实际执行的「那台机器」之间，隔着一层没有任何一致性保证的映射。一旦某个 CI 的 `client_id` 绑错了（历史遗留、机器重装后 client_id 变了、复制粘贴建档、DHCP 换 IP 后重新绑定等等都可能造成），**用户勾选 A、命令执行在 B，任务详情里显示的还是 A**。

**这不是理论推演，已经确认发生了两次：**

| 时间 | 界面上勾的 | 实际执行在 | 后果 |
|------|-----------|-----------|------|
| 8/8 | **94** | **219（平台自己）** | 94 当天**完全没有 dnf 记录**；43 个包升级在 219 上（219 有对应时刻的 ansible 被控端临时目录、当时装着 agent、无自动更新器）。219 升完后按 `needs-restarting -r` 判定重启整机 → 数据库端口被宿主机 mariadb 抢占 → **全站 502**，正在下发的任务被自己打断 |
| 8/11 | CMDB IP 记的是 **220** | **101**（该 CI 绑定的 agent 自报 IP） | 任务「已完成」，但完成在另一台机器上。**这个错位现在依然存在于库里** |

**特别提醒两点，避免走弯路：**

1. **「下发时人工不勾选平台」这类约定是无效的防线。** 8/8 那次操作者本来就没勾 219。任何依赖「操作时注意点」的流程约定都挡不住它。
2. **8/8 那次故障本身已经闭环**（平台已恢复，3306 已归位，219 上的 agent 已 mask），**本条不是要求后端补什么容错**——先前那批「长任务容错」的诉求已经撤销且不恢复。本条要修的是**产生那次故障的路由缺陷本身**，它跟 219 无关，对任何一台受管机都成立。

另外，库里有两处看起来与「排除主机」有关、但**语义无法从数据反推**的东西：`cmdb_ci` 表的 **`blacklist` 列**，和 **`workflow_run_black_hosts` 表**。两者都存在、都有数据结构，但**没有任何 UI 入口**，也没有文档说明它们在下发时到底起不起作用、按什么维度生效、谁来维护。排查时无法判断「某台机器有没有被排除」，只能靠猜。

**影响**

- **正确性**：命令可能在用户完全不知情的情况下打到错误的主机上。对 `patch install`、`reboot`、`exec` 这类操作，后果可以到「误重启生产机」这个量级。
- **可观测性**：事后从任务详情看不出打错了，只能靠去目标机上翻 dnf/日志逐台比对才能发现——8/8 那次就是这么发现的，隔了三天。
- **信任**：只要这层映射没有校验，任何一次「任务显示成功」都不能证明它成功在正确的机器上。

**期望行为**

1. **下发前做一致性校验，不一致就阻断。**
   在任务生成 / 下发的入口处，把**目标 CI 的 CMDB `host_key`（IP）** 与**该 CI 绑定的 agent 自报 IP** 做比对。不一致时**直接拒绝下发并给出明确错误**，把两个值都写进错误信息与任务日志，例如：
   `目标 CI「xxx」的 CMDB 记录 IP 为 192.168.1.220，但其绑定的 Agent（clientId=xxx）自报 IP 为 192.168.1.101，为避免命令下发到错误主机，本次下发已阻断。请先核对资产绑定关系。`
   **关键是不要再「静默地按 client_id 执行」**——现在的行为是发现不了问题的。
   > 与 B1 的关系：B1（DHCP IP 策略）讨论的是「IP 变了要不要自动改 CMDB」，属于数据维护策略；**本条讨论的是「不一致时能不能继续下发」，属于安全闸门**。两者独立，**不要等 B1 的决策**——即使最终决定 IP 不自动同步，这道闸门也必须有（届时可以做成「不一致时要求用户显式确认」而不是硬阻断，但不能没有）。

2. **识别并拒绝「目标 = 平台自身」的下发。**
   平台要能认出目标机就是自己（比较 client_id / 本机网卡 IP / 主机标识均可，建议用多个判据取并集），命中时**直接拒绝**，错误信息里写明原因。这是一道独立于运维侧 mask agent 的软件层保险——运维侧的处置只覆盖 219 这一台，代码里的判断对将来任何部署形态都成立。

3. **说明 `cmdb_ci.blacklist` 与 `workflow_run_black_hosts` 的设计语义，并补上可操作入口，或者明确废弃。**
   需要后端书面回答：这两处**在当前代码里到底还生不生效**、生效点在哪、按什么维度匹配、优先级如何。然后二选一：
   - **保留**：补 UI 入口（至少要能查看和维护「被排除的主机清单」），并在任务详情里显示「本次下发排除了哪些主机、依据是哪条规则」；
   - **废弃**：从下发链路里摘掉，并给出存量数据的处理方式。
   **现状最糟**——有机制、无入口、语义不明，排障时既不能依赖它，也不能排除它的影响。

4. **清查存量数据里还有多少 CI 存在错位，并给出清理方案。**
   跑一次全量比对，产出一份清单：CMDB IP、agent 自报 IP、client_id、最后在线时间、最近一次在其上执行过的任务。按「有错位且近期有任务下发」优先处理。清理方案需要说明：以哪一边为准（我方建议**以 agent 自报 IP 为事实、以人工确认为准**，不要脚本单向覆盖）、错位 CI 在修正前是否冻结下发、以及如何防止再次产生（例如绑定时就做一次 IP 校验）。

**验收方式**

## D1 —— DHCP 环境下，客户端 IP 变化后 CMDB 资产的主 IP 要不要自动更新？

**对应任务：** B1、F6

**我方建议：运行态 IP 自动更新，CMDB 资产主 IP 默认不覆盖，改为「检测到变化 → 提示 → 可选同步」，并提供租户级开关。**

**为什么不能「一律自动覆盖」**

1. **CMDB 主 IP 是被其它流程引用的配置真相。** 工单、审计记录、防火墙策略、文档，甚至平台自己的 SSH 纳管通道都可能按这个 IP 建立连接。静默改写它，影响面远超 Agent 模块本身，出问题时也很难追溯到「是 Agent 自动改的」。
2. **DHCP 短租约会让资产库反复抖动。** 一台笔记本一天换几次 IP，资产列表就跟着变几次，对账和报表都会受影响。
3. **主 IP 未必等于 Agent 的出口 IP。** 有的资产上人工填的是管理口地址或 VIP，而 Agent 上报的是它到平台的出口地址，两者本来就不该相同。自动覆盖会把正确的值改错。

**为什么也不能「完全不更新」**

1. 界面长期显示旧 IP，运维会以为机器还在旧地址，排障和人工 SSH 会找错目标。
2. 连通性判断需要知道「此刻」怎么连上这台机。

**为什么这样分层是安全的**

Agent 的身份锚点是 `clientId`（机器指纹）与 `clientToken`，**从来不是 IP**。所以「不更新 CMDB 主 IP」不会导致平台认错机器、也不会让 Agent 掉线——它只影响展示与人工操作的准确性，而这部分正好由「运行态 IP 自动更新 + 不一致提示」来兜住。这是两者可以拆开处理的根本原因。

**需要拍板的点**

- 是否接受「默认不覆盖 + 可选同步」这个默认值；
- 租户级自动同步开关是否要做（我方建议做，默认关闭）；
- 自动同步的收敛条件（我方建议：仅在主 IP 为空、或新 IP 已稳定两个上报周期时才自动同步）。

## D2 —— 「已注册主机重新上线」是否要走独立的 re-enroll 通道？

**对应任务：** B3、F3

**背景**

现在只有一种凭证：一次性的 enrollment token。首次纳管用它是对的，但主机被踢下线、状态文件丢失、重装系统之后想重新上线，也只能重新签发一张一次性 token 并去目标机重装一遍 Agent。现场每次都要 SSH 登录目标机。

**我方建议：为已绑定过的主机提供独立的 re-enroll 通道，不复用一次性 enrollment token。**

具体形态建议：

1. 已绑定主机的 Agent 在 `clientToken` 失效时，可凭 `clientId` + 机器指纹调用一个 `re-enroll` 接口，请求换发新的 `clientToken`；
2. 该请求默认进入「待批准」状态，管理员在控制台点「批准重新上线」即可，**不需要用户登录目标机**；
3. 可提供租户级策略：对已绑定主机的 re-enroll 自动批准（内网可信环境）或必须人工批准（更严格）。

**理由**

- 一次性 enrollment token 的设计目标是「防止凭证被滥用来纳管未授权的机器」，而 re-enroll 的对象是**平台已经认识、已经绑过资产的机器**，安全模型不同，不该套用同一种凭证。
- 现有流程的每一次重新上线都需要 SSH 登录目标机，这在桌面终端场景（Agent 的主要目标场景之一）下基本不可行——很多终端就是因为没有 SSH 才用 Agent 纳管的。

**需要拍板的点**

- 是否做独立 re-enroll 通道（不做的话，B3 就只剩「文档化 token 规则 + 支持凭证热更新」）；
- 若做，默认是「人工批准」还是「自动批准」；
- enrollment token 的默认 `ttlMinutes` 与 `maxUses` 定为多少（现在 UI 上单机默认 1 次，需要确认这是产品意图还是临时值）；
- 「安装失败也算消耗一次」是否符合预期（现在的行为是这样，现场因此困惑过多次）。

## D3 —— Windows 补丁流程是否由后端提供专用 playbook？

**对应任务：** B9（连带影响 B10、B11、F9、F10 与我方 W5）

**背景与我方判断**

见 B9。简单说：Windows 主机上没有 Python 解释器，现有 Linux playbook 在 Windows 上不可能跑通，这是 Ansible 的机制决定的，不是配置能绕过去的。

**两条路**

| 方案 | 说明 | 代价 |
|------|------|------|
| **A（推荐）** 后端为 Windows 单出 playbook | Windows 主机复用平台现有的补丁流程、任务中心、数据模型 | 后端需要新增一套 Windows playbook 与 inventory 配置 |
| B 后端不做，Windows 退回「基础通道」 | Windows 侧只做在线纳管 + exec/put/fetch，补丁能力由我方自研指令单独实现 | 与「Windows 端点含补丁能力」的既定目标不符；Windows 补丁结果无法进入平台统一的补丁/CVE 视图 |

**需要拍板的点**

选 A 还是 B。**这条不定，我方 W5（基于 WUA 的 Windows 补丁能力）无法端到端验收**，建议尽早与后端对齐。

## D4 —— 证书轮换要不要提前？（决定 Ubuntu / Debian 端点能不能走 HTTPS）

**对应任务：** F1、B4（间接影响所有受管机）
**本轮已重写：** 这条原本是一个「将来再说」的技术债，**现在有了明确的紧迫性和一个具体的截止选择**，请优先看。

**背景**

219 当前用的是一张**自签的叶子证书**：`Basic Constraints` 是 `CA:FALSE`，KeyUsage 里没有 `keyCertSign`。也就是说它**不具备 CA 的身份**，只是被当作信任锚硬塞进受管机的信任库里用。

8/11 实测确认，不同发行版对这种用法的容忍度**不一样**：

| 发行版 | OpenSSL 行为 | 结果 |
|--------|-------------|------|
| 麒麟（94） | **接受**这张叶子证书作为信任锚 | 94 已切到 HTTPS 并稳定在线 |
| Ubuntu | **拒绝**：`s_client` verify error **21**，Python 报 `CERTIFICATE_VERIFY_FAILED` | Ubuntu 上 `pip --cert`、`PIP_CERT`、`REQUESTS_CA_BUNDLE`、`update-ca-certificates` **四种办法全部失效**，只有 curl 能用 |

结论很直接：**只要还用这张证书，Ubuntu / Debian 端点就只能走 http**（已作为约束写进 F1 与 B4）。这不是配置没调对，四种标准做法都试过了。

**新增的关键信息：内网 CA 已经备好了。** 系统侧已在 219 的 `/opt/sjxy/pki/` 下准备好一套内网 CA（`Basic Constraints: CA:TRUE, pathlen:1`，KeyUsage 含 `keyCertSign`），**但尚未用它签发任何证书**。也就是说，「换成内网 CA 签发的证书」这件事**已经没有基础设施障碍了，只差一个开工决定和一个窗口期**。

**三个选项**

| 方案 | 效果 | 风险 / 代价 |
|------|------|------------|
| 维持现状（证书用到 2027-08-07 到期再说） | 零成本 | **Ubuntu / Debian 端点永久只能走 http**；长期依赖 `-k` 跳过校验，安全审计上说不过去 |
| 重新签发自签证书并补 `CA:TRUE` | 受管机可正常导入信任库 | 仍是自签，规范性不如内网 CA；**换证书同样要走全量信任链更新**，代价与下一个方案接近，性价比低 |
| **用 `/opt/sjxy/pki/` 的内网 CA 重新签发平台证书（提前轮换）** | **Ubuntu / Debian 可恢复 HTTPS**；CA 可批量预置到终端信任库；后续换叶子证书不必再动终端 | 需要一个窗口期和明确的操作顺序；**换证书会影响所有已纳管主机的 TLS 信任链**（94 上 Agent 的 `REQUESTS_CA_BUNDLE`、217 的 executor、浏览器），顺序搞错可能把已纳管主机打下线 |

**我方建议**

**建议提前轮换，用内网 CA 重签**，不要等到 2027-08-07。理由是：Ubuntu/Debian 是很可能出现在纳管范围里的发行版，为它们长期保留一条「只能走 http」的例外路径，会在前端模板、后端 `installCommand`、文档、运维手册四个地方各留一处特例，越拖越难收。CA 既然已经备好，剩下的主要是窗口期安排。

操作顺序建议：**先把内网 CA 分发并导入到所有已纳管主机与执行机 → 再切平台叶子证书 → 逐台验证 Agent 仍在线 → 最后把 F1/B4 的模板从 http/`-k` 切回严格校验的 https**。我方已做影响面评估但未动手。

**需要拍板的点**

1. 做不做提前轮换；
2. 如果做，窗口期定在什么时候（当前纳管规模小，**现在是代价最低的时间点**，以后每多纳管一台，切换成本就多一台）；
3. 在轮换完成前，**是否接受 Ubuntu / Debian 端点走 http**（这是当前 F1 的默认写法；若不接受，则 Ubuntu 端点在轮换前不能纳管）。

## D5 —— Windows Agent 的代码签名证书

**对应任务：** F8（间接影响所有 Windows 端点的安装体验）

**背景**

Windows Agent 会打包成单个 `koreops-agent.exe`。**未签名的 exe 会被 SmartScreen 弹警告，也会被主流企业 EDR 直接拦截或隔离**，尤其它还会注册系统服务、调用 Windows Update API——这些行为在未签名的情况下非常容易被判定为可疑。

**影响**

不签名的话，Windows 装机体验会很差：用户需要手工点过 SmartScreen 警告，企业环境里还得逐台加白名单，批量推广基本不可行。

**需要拍板的点**

- 是否采购代码签名证书（OV 或 EV；EV 对 SmartScreen 信誉积累更快，但价格更高、需硬件令牌）；
- 组织是否已有可复用的代码签名证书；
- 在证书到位前，是否接受「先用未签名版本做内部试点」（若接受，需要 IT 侧提前为试点机器加 EDR 白名单）。

**这条属于采购流程，周期较长，建议尽早启动，不要等到 exe 打出来才发现装不上。**
