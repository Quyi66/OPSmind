# 中间件漏洞管理 —— 前端接口文档

适用版本：2026-08-19 及之后。覆盖 WebLogic / Tomcat / Nginx 三类中间件。

统一前缀：`/sjxy-console/secops/api/secops/v2/middleware`

**一共七个接口**，对应"派发扫描 → 看扫到了什么 → 看有什么漏洞 → 怎么修 → 处置误报"这条主线：

| 接口 | 用途 |
|---|---|
| `POST /scan` | 派发扫描 |
| `GET /instances` | 实例清单（扫到了哪些中间件、每个该怎么修） |
| `GET /vuls` | 漏洞清单（有什么漏洞、修到哪个版本） |
| `GET /vuls/stats` | 漏洞概览（各定级条数 + 待确认条数） |
| `POST /vuls/ignore` | 忽略 / 取消忽略一条漏洞 |
| `GET /instances/{instanceKey}/fix-guide` | 某个实例的修复指引（步骤 + 注意事项，含无网现场流程） |
| `POST /fix` | 对 rpm/deb 分发的实例一键修复（升包 → 重启服务 → 复扫） |

早先版本还有 `GET /history`（历史趋势）、`GET /instances/summary`（按类型汇总）、
`GET /products`（产品字典）三个接口，已**移除**，不要再调：

- 趋势图不做，历史快照表连带删除；
- 类型分布用 `GET /instances?middlewareType=xxx` 取 `totalElements` 即可；
- 产品字典只有 `nginx` / `tomcat` / `weblogic` 三个值，前端直接写死。

分页返回沿用 secops 既有约定，与"已安装软件包"等列表完全一致：

```json
{
  "content": [ ... ],
  "totalElements": 137,
  "totalPages": 7,
  "size": 20,
  "number": 0,
  "first": true,
  "last": false
}
```

## 0. 先讲四件会影响 UI 设计的事

这四条不是实现细节，直接决定界面怎么摆，**动手画页面前请先看完**。

### 0.1 `unconfirmed`（待确认）必须和漏洞数分开显示

WebLogic 打补丁（PSU）**不改版本号**：打过 2026 年 7 月 PSU 的 `12.2.1.4.0` 和裸装的
`12.2.1.4.0`，版本文件里一模一样。所以只看版本号，所有规范打过补丁的机器都会被报成高危。

而"补丁号 ↔ CVE"那张对应表 Oracle 只在 MOS 登录后提供（实测公开的 925 条影响区间里
带补丁号的是 **0 条**），所以主机上采到的补丁号没法直接说明它修了哪些 CVE。

我们能公开对上的是**日期**：PSU 描述里的 `12.2.1.4.260716` 末段是 YYMMDD，
而每条 Oracle CPU 公告都有发布日期。CPU 是累积的，于是：

- PSU 日期 ≥ 公告日期 → 该期及更早的漏洞判**已修**（`fixed`）
- PSU 日期 < 公告日期 → 判**未修**（`open`）
- **采不到 PSU 日期 → 判 `unconfirmed`**

第三种情况在现场很常见（OPatch 缺失、`ORACLE_HOME` 权限不足、平台账号读不到
`inventory/`）。这些行的含义是"判不了"，不是"有漏洞"，所以：

> **`unconfirmed` 不计入漏洞总数**，在界面上单列一个"待确认"入口，
> 文案往"需要补采集条件"引导，而不是往"需要打补丁"引导。

混进总数的后果是双向的：一台其实已经打好补丁的机器显示成一堆高危；
而现场补上读权限之后数字又凭空掉下去，看起来像修了一批漏洞，其实什么都没做。

### 0.2 `provenance=rpm/deb` 的实例不出现在中间件漏洞里

发行版打包的中间件会 backport 修复而**不抬版本号**：`nginx-1.20.1-14.el8` 的版本号
还是 1.20.1，但 CVE-2021-23017 早就修了。拿上游"1.20.1 受影响"的区间去判必然误报。

这类实例已经在 Linux 补丁流水线（`patchops_curr_machine_status`）里被 rpm 口径判过一遍，
所以中间件这边**只记资产、不判漏洞**：它会出现在实例清单里（`provenance=rpm`，
漏洞计数为 0），但不会产生任何漏洞行。

这就意味着 rpm/deb 实例的漏洞数**恒为 0**。界面上不能让它显示成一个干干净净的
"无漏洞"——现场看到 rpm 装的 nginx 0 漏洞，第一反应是扫描漏了，然后就不再信这张表。
后端为此在这类实例上照样返回 `fixAction=os_package` 和一句 `fixHint`
（"由系统包管理器分发，nginx 包的漏洞与修复在 Linux 补丁模块统一管理，此处不重复判定"），
直接显示这句，并把它链到该主机的 Linux 补丁页。

这类实例也是**唯一支持一键修复**的（见 4.2）。

### 0.4 CVSS 为空要显示成 `—`，不能显示 0.0

nginx 官方公告只给 major / medium 这类定级，**不提供 CVSS 分数**（规则库里 66 条 nginx
规则有 51 条没有分数），Tomcat 部分条目同样缺。这些行 `cvss3Score` 返回的是 `null`。

前端把 `null` 渲染成 `0.0` 会被读成"无风险"——恰好和 `severity=important` 矛盾，
现场会当成数据错误。请显示为 `—`，并且**排序以 `severity` 为主**，
不要只按 CVSS 降序（否则所有 nginx 漏洞会挤在最后）。

### 0.3 `matchSource` 要露出来

`matchSource` 说明这条判定是**凭什么**得出的：

| 取值 | 含义 |
|---|---|
| `version` | 版本号落在公告给出的受影响区间内 |
| `patch_no` | 命中了公告直接给出的补丁号 |
| `psu_date` | 按 PSU 日期与公告发布日期比较得出（见 0.1） |
| `no_patch_level` | 采不到 PSU 日期，判不了 → 该行必为 `unconfirmed` |

误报是这类功能唯一会致死的问题。出现争议时要能一句话答上来"凭什么说它有漏洞"，
所以这一列不要当内部字段藏掉，建议在详情面板里直接显示。

## 1. 实例清单

`GET /instances`

| 参数 | 必填 | 说明 |
|---|---|---|
| `hostId` | 否 | CMDB 主机 id |
| `middlewareType` | 否 | `tomcat` / `weblogic` / `nginx` |
| `provenance` | 否 | `tarball` / `rpm` / `deb` / `container` / `unknown` |
| `keyword` | 否 | 按版本号或安装路径模糊匹配 |
| `page` | 否 | 从 0 开始，默认 0 |
| `size` | 否 | 默认 20，上限 500 |

`content[]` 字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| `instanceKey` | string | 实例身份，= md5(hostId\|类型\|安装路径)。后续所有按实例的操作都用它 |
| `hostId` / `hostKey` / `hostName` | string | 主机 id / 连接地址 / CMDB 名称 |
| `middlewareType` | string | 中间件类型 |
| `version` | string | 采到的版本号 |
| `installPath` / `binaryPath` | string | 安装目录 / 主程序。容器里的实例形如 `container:sjxy-web:/usr`，配合 `containerImage` 一起显示 |
| `runUser` / `pid` / `listenPorts` / `running` | - | 运行态；未运行的实例 `pid` 为 null |
| `provenance` / `pkgName` | string | 分发方式；rpm/deb 时 `pkgName` 是包名。rpm/deb 的实例不判中间件漏洞（交回 Linux 补丁流水线），`container` 照常判 |
| `containerImage` | string | 容器里的实例才有，如 `opsmind-web:2.1.7`；这类实例的整改方式是换镜像而不是打补丁 |
| `appliedPatches` | string | JSON 数组文本。**`null` 表示没采到（判不了），`[]` 表示确认没打补丁**，两者语义不同 |
| `patchLevel` | string | WebLogic 的 PSU 版本串，如 `12.2.1.4.260716` |
| `detectMethod` / `versionMethod` | string | 怎么发现的 / 怎么取到版本的，排障用 |
| `scanTimestamp` | datetime | 本条数据来自哪一轮扫描 |
| `numVuls` | int | **只含 `open`**，不含待确认 |
| `numUnconfirmed` | int | 待确认条数，单独显示 |
| `numCritical` / `numImportant` | int | `open` 里的严重 / 高危条数 |
| `fixTarget` | string | 升到这个版本可清掉该实例**全部** `open` 漏洞；WebLogic 走打补丁，此处为 null |
| `fixAction` | string | `os_package` / `container_image` / `weblogic_patch` / `upgrade` / `none`，见 1.1 |
| `fixHint` | string | 一句话动作，已含目标版本和可清掉的条数，可直接当列显示 |

### 1.1 `fixTarget` / `fixAction`：把 N 条漏洞折成一件事

漏洞清单里每条 CVE 各有自己的 `fixedVersion`，同一个实例上会散出一堆不同的目标版本 ——
现场 nginx 1.25.5 判出 24 条，官方分十次修完，于是出现十个"升级到 x.y.z"。
逐条读会以为要升十次、有二十四件事要做，**真实工作量是一件**：升到最高的那个
（`fixTarget=1.30.4`），二十四条一次全清。

所以实例清单上请以 `fixHint` 为主展示，漏洞清单里的逐条 `fixedVersion` 退为详情。
这个"最高版本"由后端用版本键算，前端不要自己比 —— 版本号按字符串比大小会把
`1.9.5` 判成高于 `1.30.4`。

`fixAction` 决定按钮怎么摆，因为同一个漏洞归谁干是不同的：

| `fixAction` | 含义 | 界面动作 |
|---|---|---|
| `os_package` | 发行版包分发，可直接一键升级 | 显示【一键修复】，调 `POST /fix` |
| `container_image` | 容器内实例，改镜像才有用 | 不给一键，展示指引；文案强调别在宿主机 yum update |
| `weblogic_patch` | 打 Oracle PSU，版本号不变 | 不给一键，展示指引（补丁包需凭 MOS 账号下载） |
| `upgrade` | 自行解压/编译部署的，换版本 + 重启 | 不给一键，展示指引 |
| `none` | 没有待修漏洞 | 不显示修复入口 |

> **为什么只有 `os_package` 能一键。** 发行版源里的中间件靠 release 号 backport 修漏洞：
> 麒麟的 `nginx` 从 `1.21.5-5.p01` 一路到 `5.p06`，主版本号始终是 1.21.5，**永远不会
> 变成上游的 1.30.4**。所以 `yum update` 能修的只有发行版包那一类；容器和自装实例在
> yum 里压根找不到上游新版本，一键下发只会无包可升，然后在界面上留下一条
> "修复已完成"的假记录。这三类的处理步骤（含无网现场怎么把包弄进来）由
> `fix-guide` 给出。

## 2. 漏洞清单

### 2.1 分页查询

`GET /vuls`

| 参数 | 必填 | 说明 |
|---|---|---|
| `hostId` | 否 | 主机 id |
| `instanceKey` | 否 | 精确到某一个安装 |
| `middlewareType` | 否 | 中间件类型 |
| `severity` | 否 | `critical` / `important` / `moderate` / `low` |
| `cveId` | 否 | 精确匹配 |
| `fixStatus` | 否 | **不传时只返回 `open`**；要看待确认传 `unconfirmed`，看已修传 `fixed` |
| `includeIgnored` | 否 | 默认 `false`，即排除已忽略的 |
| `page` / `size` | 否 | 同上，`size` 上限 500 |

排序固定为「定级降序 → CVSS 分数降序 → CVE 号降序」，照这个顺序处理就是按风险从高到低。

`content[]` 字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| `cveId` | string | CVE 号 |
| `hostId` / `hostKey` / `instanceKey` | string | 归属 |
| `middlewareType` / `installPath` | string | 哪个实例 |
| `severity` / `cvss3Score` | - | 定级与分数 |
| `currVersion` | string | 当前版本 |
| `fixedVersion` | string | **升到这个版本即修复**，见下面的注意事项。Oracle 系为空（它靠打 PSU） |
| `patchNo` | string | 公告给出的补丁号，多数为空 |
| `fixType` | string | `upgrade`（有修复版本）/ `patch`（靠打补丁） |
| `fixStatus` | string | `open` / `fixed` / `unconfirmed` / `ignored` / `mitigated` / `fixed_artificial` |
| `ignore` / `ignoreReason` | - | 用户是否标了忽略 |
| `matchSource` | string | 判定依据，见 0.3 |
| `advisoryId` | string | 公告编号，如 `TOMCAT-9.0.31` / `CPUJul2026`。纯展示文本，没有对应的公告详情接口 |
| `firstFoundAt` | datetime | **首次发现时间，跨轮保留**，算整改时效的起点 |
| `scanTimestamp` | datetime | 最近一次确认仍然存在的时间 |
| `description` / `webUrl` / `publicDate` | - | CVE 详情 |

> **`fixedVersion` 已经是"真正能修好"的版本，不是公告上写的那个。**
> 同一个 CVE 在同一条分支上可能被修好几次 —— 第一次修得不彻底，新版本又受影响。
> Tomcat 上这不是个别情况：实测 319 组组合里有 13 组踩到。最典型的是 CVE-2023-24998，
> 公告说 8.5.85 修好了，但 8.5.85 ~ 8.5.87 又受影响，实际要到 8.5.88。
> 后端已经把这种链条推到底，前端**直接展示即可**，不要再自己去公告上找修复版本。

### 2.2 统计

`GET /vuls/stats?hostId=（可选）`

```json
{
  "total": 128,
  "bySeverity": { "critical": 12, "important": 47, "moderate": 61, "low": 8 },
  "unconfirmed": 24,
  "fixed": 310,
  "ignored": 5
}
```

`total` 只含 `open`，**不含 `unconfirmed`**（理由见 0.1）。
`unconfirmed` 建议做成一个独立卡片，点进去等价于 `GET /vuls?fixStatus=unconfirmed`。

### 2.3 忽略 / 取消忽略

`POST /vuls/ignore`

```json
{ "instanceKey": "3f2a...", "cveId": "CVE-2023-21839", "ignore": true, "reason": "内网隔离，不对外提供服务" }
```

返回 `{"updated": 1}`。

`ignore` 只改用户标记，**不动机器判出来的 `fixStatus`**，所以取消忽略之后
下一轮扫描的结论照常生效，不会卡在忽略态。

## 3. 派发扫描

`POST /scan`

```json
{ "hostIds": ["ci-1001", "ci-1002"] }
```

成功返回 `{"runId": "...", "hosts": 2}`；`runId` 用来跳运行记录页。

- 按 50 台一批下发（playbook 是 linear 策略，一台卡住会堵住整批；
  WebLogic 的 `opatch lsinventory` 单机最坏两三分钟）。返回的是**首批** runId。
- 采哪些类型由后端产品字典（`patchops_mw_product` 里 `enabled=1` 的行）决定，
  不用前端传，也没有对应的查询接口。
- 扫描是异步的：接口返回只代表**派发成功**，结果要等 playbook 回调后
  才会出现在实例/漏洞清单里。前端应当轮询运行记录状态，或让用户手动刷新列表。
- 一个 `enabled` 类型都没有时返回 500 并带 `message`，此时应提示联系后端启用产品字典。

## 4. 修复

### 4.1 取修复指引

`GET /instances/{instanceKey}/fix-guide`

返回：

```json
{
  "action": "container_image",
  "canOneClick": false,
  "fixTarget": "1.30.4",
  "numVuls": 24,
  "summary": "该实例跑在容器里，修复方式是重建镜像，不是在宿主机上打补丁",
  "steps": [
    "确认镜像来源：opsmind-web:2.1.7，找到构建它的 Dockerfile 或流水线",
    "在构建侧把 nginx 从 1.25.5 升到 1.30.4（改基础镜像版本，或改镜像内安装的包版本）",
    "重新构建并推送镜像",
    "无网现场：在有网环境构建好新镜像后 docker save 成 tar，用合规介质拷到现场，在目标机 docker load 导入，再按下一步重建容器",
    "用新镜像重建容器（docker compose up -d 或 K8s 滚动更新），确认业务正常",
    "重新扫描本机中间件，确认实例版本已变为 1.30.4"
  ],
  "cautions": [
    "不要在宿主机上 yum update nginx —— 那升的是宿主机的包，容器内的二进制不会变，漏洞照旧",
    "宿主机发行版源里通常也没有 1.30.4（麒麟的 nginx 只到 1.21.5），镜像内的版本得由构建侧决定"
  ],
  "instanceKey": "...",
  "hostId": "...",
  "fixHint": "重建镜像，把 nginx 从 1.25.5 升到 1.30.4，可清掉 24 个漏洞"
}
```

`steps` / `cautions` 是按实例的实际情况（类型、分发方式、安装路径、镜像名、目标版本）
生成的，直接顺序渲染即可，不需要前端拼文案。`canOneClick=true` 时才显示【一键修复】按钮。
每条路径的 `steps` 里都带一条"无网现场怎么把包/镜像弄进来"，不要另做说明。

实例不存在返回 404。

### 4.2 一键修复（仅 rpm/deb）

`POST /fix`

```json
{
  "instanceKeys": ["796a2a10d908...", "0ec2aa90c5e8..."],
  "localPackages": { "796a2a10d908...": "/tmp/tomcat-9.0.118.rpm" }
}
```

`localPackages` 可不传。传了就用目标机上这个路径的包做本地安装，**不去连软件源** ——
这是无网现场的用法：运维把包拷到机器上（拷这一步平台代替不了），剩下的安装、重启、
复扫照样一键完成。路径不存在时自动退回从软件源升级。

成功返回：

```json
{ "runId": "5aa79384e31742b488d3b7b157d35832", "instances": 1, "skipped": [] }
```

拿 `runId` 跳运行记录看进度，和 `POST /scan` 一样。一次下发做三件事：
**升级软件包 → 重启对应服务 → 在同一个 run 里复扫本机**。所以任务结束时实例版本和
漏洞清单已经是新的，不用再手点一次扫描。实测单台 16～25 秒。

> **不走 Linux 补丁流水线的多步骤任务**（建任务 → 环境预检 → 安装 → 重启 → 校验）。
> 那套是围绕"补丁公告 × 主机"设计的，预检项（仓库可达性、dry-run 事务、rpmdb 健康、
> 磁盘、包锁）跟"把一个中间件包升到最新"这件事关系不大，却会让用户点一下之后要盯着
> 一个五步状态机。中间件这边失败的代价只是"包没升上去"，yum 自己会回滚事务。

运行记录的 `message.msg_info` 会写清楚结果，前端直接显示这句即可，例如：

```
中间件修复完成：1 台主机，成功升级 1 个实例（tomcat 9.0.10-31.ky10 → 9.0.118-1.p01.ky10）。
已顺带复扫 1 台主机，1 个实例，当前 0 个漏洞。
```

几个边界：

- 只有 `provenance` 是 `rpm`/`deb` 且采到了 `pkgName` 的实例会被下发，其余原样回在
  `skipped` 里（含被跳过的原因）；一个都不剩时返回 400。
- **软件源里已是最新**时结果是 `no_update`，运行记录仍是 COMPLETED —— 这是明确结论
  （发行版还没发布 backport），不是失败。此时引导用户看 `fix-guide` 的离线包步骤。
- 升级成功但**没找到可重启的服务**、或重启失败时，运行记录判 FAILED 并点名说明：
  老进程还跑着旧二进制，漏洞其实没修掉，必须人工重启。
- 主机 SSH 不可达时该主机点名回报"修复未执行"，不会静默消失。
- 每个实例的明细（包名、升级前后版本、服务是否重启）只进后端日志，
  搜 `mw-fix item` 即可，不入库。

## 5. 状态机与几个边界行为

| 情况 | 后端行为 | 前端应有的表现 |
|---|---|---|
| 主机没装任何中间件 | 正常结果，实例清单里该主机 0 行 | 不要报错，显示"未发现中间件" |
| `scan_status=partial`（探测超时/被拒） | **只更新、不删除**任何旧数据 | 该主机数据可能偏旧，建议加"采集不完整"角标 |
| `scan_status=failed` | 整台跳过，保留上一轮结论 | 同上，并引导去看运行记录 |
| 中间件被卸载 / 换了安装路径 | 旧实例连同它的漏洞行一起删掉 | 自然消失，无需特殊处理 |
| 实例升级到修复版本 | 该漏洞行被删掉（按扫描时间戳扫地） | 自然消失 |
| 版本号采不到 | 整个实例跳过，**不落任何漏洞行** | 实例仍在清单里（版本为空），漏洞计数 0 |

`firstFoundAt`、`ignore`、以及人工设过的 `fixStatus`
（`ignored` / `mitigated` / `fixed_artificial`）在扫描覆盖时都会被保留，
前端可以放心把它们当作持久数据。
