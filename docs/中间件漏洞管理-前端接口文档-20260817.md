# 中间件漏洞管理 —— 前端接口文档

适用版本：2026-08-17 及之后。覆盖 WebLogic / Tomcat / Nginx 三类中间件的实例清单、
漏洞清单、统计、忽略、历史趋势与扫描派发。

统一前缀：`/sjxy-console/secops/api/secops/v2/middleware`

分页返回沿用 secops 既有约定，与"已安装软件包"等列表完全一致：

```json
{
  "content": [ ... ],
  "totalElements": 137,
  "totalPages": 7,
  "size": 20,
  "number": 0,
  "first": true,
  "last": false
}
```

## 0. 先讲三件会影响 UI 设计的事

这三条不是实现细节，直接决定界面怎么摆，**动手画页面前请先看完**。

### 0.1 `unconfirmed`（待确认）必须和漏洞数分开显示

WebLogic 打补丁（PSU）**不改版本号**：打过 2026 年 7 月 PSU 的 `12.2.1.4.0` 和裸装的
`12.2.1.4.0`，版本文件里一模一样。所以只看版本号，所有规范打过补丁的机器都会被报成高危。

而"补丁号 ↔ CVE"那张对应表 Oracle 只在 MOS 登录后提供（实测公开的 925 条影响区间里
带补丁号的是 **0 条**），所以主机上采到的补丁号没法直接说明它修了哪些 CVE。

我们能公开对上的是**日期**：PSU 描述里的 `12.2.1.4.260716` 末段是 YYMMDD，
而每条 Oracle CPU 公告都有发布日期。CPU 是累积的，于是：

- PSU 日期 ≥ 公告日期 → 该期及更早的漏洞判**已修**（`fixed`）
- PSU 日期 < 公告日期 → 判**未修**（`open`）
- **采不到 PSU 日期 → 判 `unconfirmed`**

第三种情况在现场很常见（OPatch 缺失、`ORACLE_HOME` 权限不足、平台账号读不到
`inventory/`）。这些行的含义是"判不了"，不是"有漏洞"，所以：

> **`unconfirmed` 不计入漏洞总数**，在界面上单列一个"待确认"入口，
> 文案往"需要补采集条件"引导，而不是往"需要打补丁"引导。

混进总数的后果是双向的：一台其实已经打好补丁的机器显示成一堆高危；
而现场补上读权限之后数字又凭空掉下去，看起来像修了一批漏洞，其实什么都没做。

### 0.2 `provenance=rpm/deb` 的实例不出现在中间件漏洞里

发行版打包的中间件会 backport 修复而**不抬版本号**：`nginx-1.20.1-14.el8` 的版本号
还是 1.20.1，但 CVE-2021-23017 早就修了。拿上游"1.20.1 受影响"的区间去判必然误报。

这类实例已经在 Linux 补丁流水线（`patchops_curr_machine_status`）里被 rpm 口径判过一遍，
所以中间件这边**只记资产、不判漏洞**：它会出现在实例清单里（`provenance=rpm`，
漏洞计数为 0），但不会产生任何漏洞行。

界面上建议在这类实例行加一个说明角标，链到该主机的 Linux 补丁页，
否则用户会以为"这个 nginx 没扫"。

### 0.3 `matchSource` 要露出来

`matchSource` 说明这条判定是**凭什么**得出的：

| 取值 | 含义 |
|---|---|
| `version` | 版本号落在公告给出的受影响区间内 |
| `patch_no` | 命中了公告直接给出的补丁号 |
| `psu_date` | 按 PSU 日期与公告发布日期比较得出（见 0.1） |
| `no_patch_level` | 采不到 PSU 日期，判不了 → 该行必为 `unconfirmed` |

误报是这类功能唯一会致死的问题。出现争议时要能一句话答上来"凭什么说它有漏洞"，
所以这一列不要当内部字段藏掉，建议在详情面板里直接显示。

## 1. 实例清单

### 1.1 分页查询

`GET /instances`

| 参数 | 必填 | 说明 |
|---|---|---|
| `hostId` | 否 | CMDB 主机 id |
| `middlewareType` | 否 | `tomcat` / `weblogic` / `nginx` |
| `provenance` | 否 | `tarball` / `rpm` / `deb` / `container` / `unknown` |
| `keyword` | 否 | 按版本号或安装路径模糊匹配 |
| `page` | 否 | 从 0 开始，默认 0 |
| `size` | 否 | 默认 20，上限 500 |

`content[]` 字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| `instanceKey` | string | 实例身份，= md5(hostId\|类型\|安装路径)。后续所有按实例的操作都用它 |
| `hostId` / `hostKey` / `hostName` | string | 主机 id / 连接地址 / CMDB 名称 |
| `middlewareType` | string | 中间件类型 |
| `version` | string | 采到的版本号 |
| `installPath` / `binaryPath` | string | 安装目录 / 主程序 |
| `runUser` / `pid` / `listenPorts` / `running` | - | 运行态；未运行的实例 `pid` 为 null |
| `provenance` / `pkgName` | string | 分发方式；rpm/deb 时 `pkgName` 是包名 |
| `containerImage` | string | 容器里的实例才有 |
| `appliedPatches` | string | JSON 数组文本。**`null` 表示没采到（判不了），`[]` 表示确认没打补丁**，两者语义不同 |
| `patchLevel` | string | WebLogic 的 PSU 版本串，如 `12.2.1.4.260716` |
| `detectMethod` / `versionMethod` | string | 怎么发现的 / 怎么取到版本的，排障用 |
| `scanTimestamp` | datetime | 本条数据来自哪一轮扫描 |
| `numVuls` | int | **只含 `open`**，不含待确认 |
| `numUnconfirmed` | int | 待确认条数，单独显示 |
| `numCritical` / `numImportant` | int | `open` 里的严重 / 高危条数 |

`GET /instances/summary` → `[{"middlewareType":"tomcat","cnt":42}, ...]`

## 2. 漏洞清单

### 2.1 分页查询

`GET /vuls`

| 参数 | 必填 | 说明 |
|---|---|---|
| `hostId` | 否 | 主机 id |
| `instanceKey` | 否 | 精确到某一个安装 |
| `middlewareType` | 否 | 中间件类型 |
| `severity` | 否 | `critical` / `important` / `moderate` / `low` |
| `cveId` | 否 | 精确匹配 |
| `fixStatus` | 否 | **不传时只返回 `open`**；要看待确认传 `unconfirmed`，看已修传 `fixed` |
| `includeIgnored` | 否 | 默认 `false`，即排除已忽略的 |
| `page` / `size` | 否 | 同上，`size` 上限 500 |

排序固定为「定级降序 → CVSS 分数降序 → CVE 号降序」，照这个顺序处理就是按风险从高到低。

`content[]` 字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| `cveId` | string | CVE 号 |
| `hostId` / `hostKey` / `instanceKey` | string | 归属 |
| `middlewareType` / `installPath` | string | 哪个实例 |
| `severity` / `cvss3Score` | - | 定级与分数 |
| `currVersion` | string | 当前版本 |
| `fixedVersion` | string | **升到这个版本即修复**，见下面的注意事项。Oracle 系为空（它靠打 PSU） |
| `patchNo` | string | 公告给出的补丁号，多数为空 |
| `fixType` | string | `upgrade`（有修复版本）/ `patch`（靠打补丁） |
| `fixStatus` | string | `open` / `fixed` / `unconfirmed` / `ignored` / `mitigated` / `fixed_artificial` |
| `ignore` / `ignoreReason` | - | 用户是否标了忽略 |
| `matchSource` | string | 判定依据，见 0.3 |
| `advisoryId` | string | 关联公告，如 `TOMCAT-9.0.31` / `CPUJul2026` |
| `firstFoundAt` | datetime | **首次发现时间，跨轮保留**，算整改时效的起点 |
| `scanTimestamp` | datetime | 最近一次确认仍然存在的时间 |
| `description` / `webUrl` / `publicDate` | - | CVE 详情 |

> **`fixedVersion` 已经是"真正能修好"的版本，不是公告上写的那个。**
> 同一个 CVE 在同一条分支上可能被修好几次 —— 第一次修得不彻底，新版本又受影响。
> Tomcat 上这不是个别情况：实测 319 组组合里有 13 组踩到。最典型的是 CVE-2023-24998，
> 公告说 8.5.85 修好了，但 8.5.85 ~ 8.5.87 又受影响，实际要到 8.5.88。
> 后端已经把这种链条推到底，前端**直接展示即可**，不要再自己去公告上找修复版本。

### 2.2 统计

`GET /vuls/stats?hostId=（可选）`

```json
{
  "total": 128,
  "bySeverity": { "critical": 12, "important": 47, "moderate": 61, "low": 8 },
  "unconfirmed": 24,
  "fixed": 310,
  "ignored": 5
}
```

`total` 只含 `open`，**不含 `unconfirmed`**（理由见 0.1）。
`unconfirmed` 建议做成一个独立卡片，点进去等价于 `GET /vuls?fixStatus=unconfirmed`。

### 2.3 忽略 / 取消忽略

`POST /vuls/ignore`

```json
{ "instanceKey": "3f2a...", "cveId": "CVE-2023-21839", "ignore": true, "reason": "内网隔离，不对外提供服务" }
```

返回 `{"updated": 1}`。

`ignore` 只改用户标记，**不动机器判出来的 `fixStatus`**，所以取消忽略之后
下一轮扫描的结论照常生效，不会卡在忽略态。

## 3. 历史趋势

`GET /history?hostId=xxx&limit=30`

每轮扫描一行，倒序返回。`limit` 默认 30、上限 365。

关键字段：`scanTimestamp`、`instanceCount`、`middlewareTypes`、
`numCritical` / `numImportant` / `numModerate` / `numLow`、
`numVuls`（只含 open）、`numUnconfirmed`、`scanStatus`、
`instances`（该轮实例摘要的 JSON 快照）。

画趋势图建议画两条线：`numVuls` 和 `numUnconfirmed`。
只画一条合起来的会出现 0.1 里说的那种"假修复"台阶。

## 4. 产品字典

`GET /products`

返回 `patchops_mw_product` 全部行。`enabled=1` 的类型才会下发给主机采集，
所以这个接口既是字典也是"当前采什么"的说明。

`patchLevelAware=true` 表示该产品打补丁不抬版本号（目前只有 WebLogic），
这类产品的漏洞判定会走 PSU 日期口径，也只有这类产品会出现 `unconfirmed`。

## 5. 派发扫描

`POST /scan`

```json
{ "hostIds": ["ci-1001", "ci-1002"] }
```

成功返回 `{"runId": "...", "hosts": 2}`；`runId` 用来跳运行记录页。

- 按 50 台一批下发（playbook 是 linear 策略，一台卡住会堵住整批；
  WebLogic 的 `opatch lsinventory` 单机最坏两三分钟）。返回的是**首批** runId。
- 采哪些类型由产品字典里 `enabled=1` 的行决定，不用前端传。
- 扫描是异步的：接口返回只代表**派发成功**，结果要等 playbook 回调后
  才会出现在实例/漏洞清单里。前端应当轮询运行记录状态，或让用户手动刷新列表。
- 一个 `enabled` 类型都没有时返回 500 并带 `message`，此时应提示去产品字典里启用。

## 6. 状态机与几个边界行为

| 情况 | 后端行为 | 前端应有的表现 |
|---|---|---|
| 主机没装任何中间件 | 正常结果，实例清单里该主机 0 行 | 不要报错，显示"未发现中间件" |
| `scan_status=partial`（探测超时/被拒） | **只更新、不删除**任何旧数据 | 该主机数据可能偏旧，建议加"采集不完整"角标 |
| `scan_status=failed` | 整台跳过，保留上一轮结论 | 同上，并引导去看运行记录 |
| 中间件被卸载 / 换了安装路径 | 旧实例连同它的漏洞行一起删掉 | 自然消失，无需特殊处理 |
| 实例升级到修复版本 | 该漏洞行被删掉（按扫描时间戳扫地） | 自然消失 |
| 版本号采不到 | 整个实例跳过，**不落任何漏洞行** | 实例仍在清单里（版本为空），漏洞计数 0 |

`firstFoundAt`、`ignore`、以及人工设过的 `fixStatus`
（`ignored` / `mitigated` / `fixed_artificial`）在扫描覆盖时都会被保留，
前端可以放心把它们当作持久数据。
