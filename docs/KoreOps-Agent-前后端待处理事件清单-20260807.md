# KoreOps Agent 联调 — 前后端待处理事件清单

**日期：** 2026-08-07
**性质：** 从 8/3、8/5 两份详细排查报告中提炎出的、**需要前端或后端实际动手处理**的事项清单。深入的实测证据、命令、根因分析见文末《参考材料》里的两份完整报告，本清单只列结论和动作，方便直接分给对应的人。
**适用范围：** 以下问题在 `192.168.1.162` 上实测发现；`192.168.1.219`（新平台，镶像与 162 同版本 `sjxy:3.7.8` / `opsmind-web:2.1.7`）已复核确认**同样全部存在**，属于镜像/代码层面的问题，不是环境个例。

## 一、后端（BE）待处理事件

| # | 严重度 | 问题 | 现象 | 何时发现 |
|---|--------|------|------|----------|
| B1 | **P0** | Console 包 `shiro.properties` 里 `agent/api/agent` 的 anon 规则从 **4 条变成 0 条** | `POST /sjxy-console/agent/api/agent/register` 返回 **Spring 层 401**（请求在鉴权层被拦，进不到业务代码） | 8/5 新增回归 |
| B2 | **P0** | Dashboard 包内**没有 Agent 相关代码**（`cmdb/agent/*.class` 数量为 0，应为 23） | Agent 注册/纳管/CVE 相关 CMDB 接口全部 404 或无法工作 | 8/3 首次发现，至今未修复 |
| B3 | **P0** | 无「登录态签发 enrollment token」的管理 API 或 UI 入口 | 只能靠后端手工操作数据库/接口出 token，前端/运维无法自助签发，联调被反复卡在这一步 | 7/29 起持续存在 |
| B4 | P1 | Agent 静态分发文件（`install.sh` 等）的 nginx `location` 是**运行时改容器**打进去的，不在镜像模板或挂载卷里 | `sjxy-web`/`opsmind-web` 容器一旦重建（发版、扩容、故障重启都会触发），`install.sh` 立刻退回 401，需要人工再手动改一次，反复发生 | 8/3 推断，8/5 已实测复现（R1） |
| B5 | P1 | War 文件本身也不在挂载卷里，在容器可写层 | 同上，容器重建后 war 会退回镜像里自带的旧/坑版本，之前任何"手动恢复"都不持久 | 8/3 推断，8/5 已实测复现 |
| B6 | P1 | `/opt/sjxy/.sjxy-env.yml` 权限 **644**，其中**明文**存放 relay internal-token | 与后端自己的部署文档 §8 安全检查项（要求 0600）不符；我方未擅自改权限，因不确定容器以何身份读取该文件 | 8/3（E3） |
| B7 | P2 | `agent.py.sha256` 曾缺精确匹配的 nginx location，导致完整性校验形同虚设 | 该 URL 曾返回 401（被代理到后端应用而非当静态文件返回） | 8/3（E2），8/5 的修复方案里已顺带给出补丁，但需要后端/运维实际落地到持久化模板 |
| B8 | 待评估 | `agent_enrollment_token`、`host_agent_binding` 两张表存在，但**完整业务闭环从未在一个"功能齐全"的 war 上跑通过** | B1/B2 修好之前，闭环验证一直无法进行；219 上目前连这两张表都还没有（全新库，从未跑过迁移） | 持续 |

**给后端的一句话总结：** B1+B2 两个都修好、且解决 B4/B5 的持久化方式之后，8/3 报告 §0 给出的验收标准即可直接复测；届时我方只需拿到一个 token，10 分钟内可跑完端到端联调。**目前 162 上"最后一份还完好的 console+dashboard 包"已经被后续几次自动构建覆盖掉了**（我方已从 docker 残留层里只读抢救出一份备份自用于 219 测试，162 现网本身未受任何影响），建议后端后续构建流程里增加"anon 规则数=4、agent class 数=23"这两条判据作为发版前的自动校验，避免同类回归再次发生。

## 二、前端（FE）待处理事件

| # | 严重度 | 问题 | 现象 | 影响 |
|---|--------|------|------|------|
| F1 | **P0** | KoreOPS 控制面里**没有 Agent 管理 / Agent 接入的入口** | 「资产管理」录入主机只有 IP 字段，走 SSH；找不到任何页面能签发 enrollment token 或查看 Agent 状态 | 直接导致运维/管理员无法自助纳管 Agent 主机，必须找后端手工处理，联调效率很低 |
| F2 | P1 | 主机列表/详情缺少 Agent 相关字段展示 | 无 `connectionType`、`agentStatus`、`clientId`、`capabilities`、`lastSeenAt` 等列 | 无法在界面上分辨一台主机是 SSH 纳管还是 Agent 纳管、是否在线 |
| F3 | P1 | 任务详情不显示执行通道 | 看不出一次任务是走 `ssh` 还是走 `koreops_agent` | 排查问题时无法快速定位是通道问题还是业务问题 |

**说明：** F1 是最优先的一条——只要后端把 B3（签发 API）做出来，前端只需要给它一个入口即可，工作量不大但对打通联调是刚需。F2/F3 依赖后端 B1/B2 修好、主机查询接口把相关字段吐出来之后才能真正对接，可以先设计原型，不阻塞。更细的前端任务分解（纳管向导、按钮启用/禁用规则、错误提示等）见文末《联调任务单》。
